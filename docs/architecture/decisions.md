# Architecture Decision Records (léger)

Format court : **Contexte** (pourquoi se pose la question) → **Décision** (ce qu'on fait) → **Conséquences** (coûts / contraintes / choix que ça ferme). Datées, pas numérotées — l'ordre chronologique suffit.

## ADR-01 · 2025-Q4 · Hébergement front sur GitHub Pages

- **Contexte** : besoin d'un cockpit perso déployable sans infra, pas de build CI lourd, accessible depuis mobile.
- **Décision** : GitHub Pages servit en statique, coquille `index.html` + React 18 via `@babel/standalone` sur unpkg. No-build-step.
- **Conséquences** : CSP doit autoriser `unsafe-eval` (Babel standalone) ; pas de tree-shaking ; chaque `.jsx` expose son composant sur `window.X` pour être visible par les autres scripts ; itération possible en `file://` local sans serveur.

## ADR-02 · 2025-Q4 · Supabase comme backend unique

- **Contexte** : stockage structuré des articles, métriques et conversations + auth Google + RLS granulaire, sans ouvrir un serveur perso.
- **Décision** : Supabase free tier, Postgres + pgvector + Auth Google + Realtime. Toute la donnée structurée y vit.
- **Conséquences** : une seule cible de RLS à auditer ; quotas 500 MB / 50k MAU à surveiller (panel Stacks) ; dépendance cloud unique — si Supabase tombe, Jarvis local reste dispo mais le cockpit lit vide.

## ADR-03 · 2026-Q1 · Split Gemini (daily) / Claude (weekly)

- **Contexte** : la veille quotidienne traite ~150 articles / jour (enrichissement, classification, brief) — incompatible avec le budget Claude. Mais les analyses hebdo (signaux, opportunités, challenges, recos) demandent un modèle de bien meilleure qualité.
- **Décision** : Gemini 2.5 Flash-Lite (free tier 1000 req/jour) pour tout le volume daily. Claude Haiku 4.5 (budget ~0,03 $/run, cap 1 $) pour la cognition hebdo.
- **Conséquences** : deux clients, deux clés, deux pipelines à logger distinctement (tables `gemini_api_calls` + `weekly_analysis.tokens_used`). Panel Stacks agrège les deux. Si Gemini tombe, le daily a un fallback `_fallback_brief_html` qui construit un brief minimal depuis les articles RSS.

## ADR-04 · 2026-Q1 · Pipelines backend en `service_role`, front en `authenticated`

- **Contexte** : les pipelines GitHub Actions tournent sans session `auth.uid()` — ils ne peuvent pas être des utilisateurs `authenticated`. Le front lui a une session Google OAuth.
- **Décision** : migration `sql/006_rls_authenticated.sql` — toutes les tables exigent `authenticated` pour SELECT. Les tables éditées par le front (~16 aujourd'hui : `business_ideas`, `user_profile`, `skill_radar`, `weekly_opportunities`, `learning_recommendations`, `challenge_attempts`, `wiki_concepts`, `commitments`, `uncomfortable_questions`, `gaming_wishlist`, `history_notes`, `claude_veille`, `claude_ecosystem`, `profile_facts`, `usage_events`, `jobs`) ont aussi INSERT/UPDATE `authenticated` — voir `dependencies.yaml::panels[].writes` pour la liste vivante. Les pipelines utilisent `SUPABASE_SERVICE_KEY` qui bypass RLS.
- **Conséquences** : anon ne peut plus rien lire (fini le partage public du cockpit sans login) ; `start_jarvis.bat` refuse de démarrer sans `SUPABASE_SERVICE_KEY` en env ; chaque nouvelle table ajoutée doit explicitement configurer ses policies (cf. migrations récentes). Exception : `jobs` et `job_scans` sont en `using(true)` (pas restreints `authenticated`) — divergence assumée pour la routine Cowork qui pousse en service_role mais pour laquelle l'écriture reste whitelistée côté front sur `status` + `user_notes`.

## ADR-05 · 2026-Q1 · Data layer front à deux tiers

- **Contexte** : certains panels (Brief, Ma semaine, Radar) doivent s'afficher instantanément au premier écran. Les autres peuvent charger à la demande. Charger 40 tables au boot = latence inacceptable.
- **Décision** : **Tier 1** (bootstrap.js → bootTier1) charge 7 tables en parallèle AVANT le mount React ; **Tier 2** (loadPanel) charge le corpus d'un panel à son premier clic sidebar, mémoïsé via `once()` le reste de la session.
- **Conséquences** : chaque panel déclare explicitement s'il est Tier 1 ou Tier 2 ; cache Tier 2 est invalidé seulement au reload (pas de cache busting sélectif) ; un nouveau panel par défaut est Tier 2 sauf décision contraire.

## ADR-06 · 2026-Q1 · Jarvis local FastAPI + tunnel Cloudflare optionnel

- **Contexte** : on veut un assistant IA perso qui connaît nos faits, avec RAG sur notre corpus Supabase. Un SaaS type ChatGPT ne peut pas (privacy + coût).
- **Décision** : `jarvis/server.py` (FastAPI uvicorn port 8765) appelle LM Studio local (Qwen3.5 9B) ou Claude Haiku selon le mode. Le cockpit appelle `POST /chat` — localhost d'abord, puis tunnel Cloudflare en fallback quand le cockpit tourne sur GitHub Pages (HTTPS interdit le mixed-content vers `http://localhost`).
- **Conséquences** : l'utilisateur doit lancer `start_jarvis.bat` pour que Jarvis réponde ; URL du tunnel est publiée dans `user_profile.jarvis_tunnel_url` ; si tunnel down, fallback heuristique local dégradé (mode Pratique des challenges surtout).

## ADR-07 · 2026-Q2 · Observers privacy-first (données locales uniquement)

- **Contexte** : Jarvis a besoin de comprendre ce que l'utilisateur fait en ce moment (fenêtre active, calendrier, mails) pour répondre pertinemment. Mais on ne veut PAS que ces données partent sur un serveur tiers.
- **Décision** : observers (`window_observer.py`, `outlook_observer.py`) stockent les données brutes dans `jarvis_data/*.jsonl` / `.json` locaux, jamais versionnés. Seul un résumé quotidien agrégé (`activity_briefs`) monte dans Supabase, via `daily_brief_generator.py` à 18h.
- **Conséquences** : les titres de réunions et apps actives restent sur la machine locale ; si on change de machine, tout l'historique d'activité brute est perdu (résumés conservés) ; le `nightly_learner.py` qui extrait les faits depuis ces JSONL doit tourner sur la machine qui les produit.

## ADR-08 · 2026-Q2 · Pipelines perso séparés, pas de monolithe sync.py

- **Contexte** : au début on avait `main.py` qui faisait tout (RSS + stats perso). Devenu ingérable, différents rythmes, différentes APIs, différents formats.
- **Décision** : un `pipelines/<source>_sync.py` par source externe (Strava, Withings, Last.fm, Steam, Sport RSS, Gaming RSS, Anime RSS, News RSS), chacun avec son workflow YAML dédié et son cron propre. `requirements-<source>.txt` isolé pour éviter les conflits de deps.
- **Conséquences** : 10 pipelines au lieu d'un, mais chacun petit et testable indépendamment ; coût : 10 workflows à maintenir ; un bug sur Strava ne casse pas Last.fm.

## ADR-09 · 2026-Q2 · Stockage brut + mappé pour chaque source externe

- **Contexte** : les APIs externes évoluent (Strava change ses schémas, Withings ajoute des champs). Si on ne stocke que la forme mappée, on perd l'info.
- **Décision** : chaque source a DEUX tables — `<source>_raw` (payload JSONB complet, service_role only) et `<source>_<entity>` (colonnes typées lues par le front). Le pipeline upsert les deux.
- **Conséquences** : double stockage donc coût disque + ; mais on peut toujours re-mapper sans refetch depuis l'API (précieux sur les APIs à rate-limit sévère type Strava).

## ADR-10 · 2026-Q2 · pgvector + indexer Jarvis unifié

- **Contexte** : Jarvis a besoin de RAG sur articles + wiki + opportunités + idées + RTE + profil. Utiliser 6 tables distinctes pour l'embedding serait ingérable.
- **Décision** : une table `memories_vectors` unique (source_table + source_id + chunk_text + embedding vector(1024) + metadata JSONB). `jarvis/indexer.py` indexe périodiquement chaque table source. Fonction RPC `match_memories()` pour la recherche sémantique.
- **Conséquences** : un seul index à gérer ; dimension 1024 figée (modèle Qwen3-Embedding-0.6B) — changer de modèle = réindexer tout ; `check_index_freshness.py` compare les COUNTs source vs `memories_vectors` au boot de Jarvis.

## ADR-11 · 2026-Q2 · Télémétrie append-only dans `usage_events`

- **Contexte** : on veut savoir ce que l'utilisateur fait dans le cockpit (sections visitées, actions, erreurs) sans maintenir un SaaS analytics.
- **Décision** : table `usage_events` append-only (INSERT authenticated, pas de UPDATE/DELETE enforcé par RLS). Le front envoie via `track(event_type, payload)` best-effort. Un échec de télémétrie ne casse jamais le cockpit.
- **Conséquences** : données rétrocompatibles par construction (JSONB `payload` extensible) ; panel Historique consomme directement `usage_events` pour les "actions du jour" ; ajouter un nouvel `event_type` demande de mettre à jour le tableau dans CLAUDE.md.

## ADR-12 · 2026-Q2 · Specs produit par onglet + lint bloquant

- **Contexte** : les 29 onglets du cockpit dérivaient vite du code — personne ne savait ce qu'ils étaient censés faire.
- **Décision** : un `docs/specs/tab-<slug>.md` par onglet, source de vérité consommée en direct par Jarvis Lab. Sections `Fonctionnalités` et `Parcours utilisateur` écrites en vocabulaire produit (pas de chemins `.jsx`, pas de `Tier 1`, pas de colonnes DB). Lint bloquant CI (`lint_specs_produit.py`).
- **Conséquences** : toute PR de code à impact sur un onglet doit updater son spec dans le même commit ; drift automatiquement détecté par `spec-drift-check.yml` ; lint CI bloque les régressions de vocabulaire.

## ADR-13 · 2026-Q2 · Architecture en YAML, rendu SVG maison (pas Mermaid)

- **Contexte** : on veut une vue archi dans Jarvis Lab, versionnée, avec des règles de routage strictes (pas de diagonales, trois types d'arêtes dans trois couloirs, labels verticaux à gauche). Mermaid ne sait pas faire proprement, et son thème ignore nos CSS variables Dawn/Obsidian/Atlas.
- **Décision** : `docs/architecture/*.yaml` déclaratif, rendu par un composant React custom qui calcule les positions et les rails de routage. js-yaml côté client pour parser. Lint `validate_architecture.py` + arch-drift-check côté CI.
- **Conséquences** : écrire le renderer maison = 500+ lignes de SVG layout ; mais on contrôle le routage à 100 % et on hérite des 3 thèmes gratos via `var(--acc)` ; ajouter une 5e boîte à une couche redistribue automatiquement les colonnes.

## ADR-14 · 2026-Q2 · Budget dur 3 €/mois, tracking Stacks

- **Contexte** : projet perso, pas question de se retrouver avec une facture 30 € pour avoir oublié de capper un quota.
- **Décision** : budget mensuel hard à 3 € (Claude Haiku weekly + Jarvis cloud occasionnel). `CostTracker` dans `weekly_analysis.py` arrête le pipeline si le budget hebdo dépasse 1 $. Panel Stacks agrège les coûts réels + projection 7j.
- **Conséquences** : les analyses hebdo peuvent s'arrêter avant d'être complètes certains runs ; on est forcé à écrire des prompts compacts ; Gemini free tier reste la cheville ouvrière.

## ADR-16 · 2026-05-21 · Calibrage Jobs Radar par feedback utilisateur

- **Contexte** : le scoring Cowork (0-10) est calculé sans retour utilisateur — après 2 mois d'usage, le radar remonte des offres systématiquement mal scorées (trop junior, mauvais secteur). On veut un signal de calibrage sans créer un nouveau pipeline.
- **Décision** : signal 👍/👎 + raison persisté sur 3 nouvelles colonnes de la table `jobs` (`user_verdict` text, `user_verdict_reason` text, `user_verdict_at` timestamptz — migration 014, `sql/014_jobs_feedback.sql`). Héritage du verdict sur republication LinkedIn dans la même fenêtre 180j (extension du trigger `jobs_inherit_user_status`). Préférences utilisateur découpées en deux clés `user_profile` : `job_pref_rules` (règles verouillées par l'utilisateur, non écrasables) et `job_pref_observed` (profil inféré et maintenu par la routine Cowork à chaque run). La synthèse feedback → ajustement score s'exécute à l'intérieur du run Cowork quotidien existant, sans nouveau pipeline. Pas de second score : le verdict ajuste directement `score_total` au prochain scan. Effet asynchrone : un vote aujourd'hui influe sur le scan du lendemain.
- **Conséquences** : trois colonnes nullable sur `jobs` (whitelist front élargie) ; routine Cowork versionnée à mettre à jour (`docs/cowork-routines/jobs-radar.md`) pour lire `job_pref_rules` + `job_pref_observed` + les verdicts récents avant scoring ; `user_profile` gagne deux clés JSONB structurées à documenter dans la spec profil ; fenêtre d'héritage passée de 30j (archived) à 180j pour couvrir les verdicts.

## ADR-18 · 2026-05-27 · Clôture manuelle — le front écrit `closed_at`

- **Contexte** : ADR-17 a posé `closed_at` en écriture Cowork seule (lecture seule côté front). La détection reste asynchrone — une offre clôturée peut traîner dans le feed plusieurs jours avant la passe de fraîcheur, et l'utilisateur n'a aucun moyen de la masquer immédiatement quand il tombe sur le mur LinkedIn.
- **Décision** : le cockpit peut désormais écrire `closed_at` via un bouton « Marquer clôturée » (et « Rouvrir » qui le remet à NULL). `closed_at` rejoint la whitelist `patchJobSupabase` (comme `user_verdict*` avant lui). **Renverse** la conséquence d'ADR-17 « jamais écrit par le cockpit ». La détection Cowork (opportuniste + passe de fraîcheur re-priorisée, cf. routine v3.2) reste en place — les deux chemins coexistent, `isDead(o)` les unifie.
- **Conséquences** : `closed_at` écrit par deux sources (Cowork auto + front manuel) ; réversibilité front (Rouvrir) ; télémétrie `jobs_action {action:"close"|"reopen"}` ; RLS `jobs` déjà permissive (`using(true)`) → pas de changement de policy ; `dependencies.yaml` whitelist à jour.

## ADR-17 · 2026-05-21 · Offres clôturées — détection Cowork + masquage front

- **Contexte** : certaines offres LinkedIn restent actives en base longtemps après que LinkedIn les ait marquées "Les candidatures ne sont plus acceptées". Le cockpit continue d'afficher ces offres mortes, polluant le feed. On ne peut pas vérifier LinkedIn en direct côté cockpit (pas d'accès authentifié, pas de scraping front possible).
- **Décision** : colonne `closed_at timestamptz` ajoutée à la table `jobs` (migration 015, `sql/015_jobs_closed_at.sql`). La routine Cowork la pose à `now()` quand elle lit "ne sont plus acceptées" / "No longer accepting applications" lors d'une visite de page d'offre (opportuniste à l'Étape 5 sur les nouvelles offres, ou lors d'une passe de fraîcheur Étape 8 sur les 25 offres actives les plus anciennes). Le front masque toute offre avec `closed_at non-null && status !== "applied"` dans le feed actif et les hot leads. Filtre "Clôturées" dédié pour les revoir. Compteur header ("N clôturées masquées") si N > 0. Une offre déjà postulée (status="applied") reste visible dans le pipeline malgré `closed_at`.
- **Conséquences** : masquage précis — jamais sur la seule ancienneté `last_seen_date` (risque de cacher des offres valides) ; effet asynchrone (délai entre la clôture LinkedIn et la détection Cowork) ; `closed_at` n'est pas dans la whitelist PATCH front (jamais écrit par le cockpit) ; la passe de fraîcheur est bornée à 25 offres/run pour tenir le budget 15 min.

## ADR-15 · 2026-Q2 · Maintenance archi versionnée avec CI arch-drift

- **Contexte** : la doc archi dérive toujours plus vite que le code. On ne veut pas reproduire l'erreur des specs onglets.
- **Décision** : workflow `arch-drift-check.yml` qui liste les chemins à impact archi (pipelines/, main.py, panel-*.jsx, migrations, workflows sync) et warn quand une PR touche l'un sans toucher `docs/architecture/`. Workflow `validate-arch.yml` bloquant sur structure des YAML. CLAUDE.md § Maintenance architecture aligné sur la section specs.
- **Conséquences** : non-bloquant au départ (`continue-on-error: true`) — on durcira après deux semaines de bruit ; la checklist par type de modif (nouveau pipeline / nouveau panel / nouvelle table) est explicite dans le README archi et dans CLAUDE.md.

## ADR-19 · 2026-05-28 · Jobs Radar — routine Claude Code distante (JSearch) remplace la routine Cowork LinkedIn

- **Contexte** : la routine Cowork (Sonnet + navigateur sur session LinkedIn, cf. [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)) était token-vore (~0,20-0,40 €/run) — ingestion de DOM LinkedIn rendus + navigation du graphe social pour l'intel warm — et dépendait d'un Chrome authentifié + Cowork desktop allumé. Le design du 2026-05-27 ([specs/2026-05-27-jobs-radar-api-migration-design](../superpowers/specs/2026-05-27-jobs-radar-api-migration-design.md)) proposait une routine Claude Code distante sur API jobs structurée. Un plan intermédiaire (2026-05-28) a tenté un pivot vers un cron GitHub Actions + Gemini gratuit, sur la crainte qu'un agent distant ne puisse pas s'authentifier — **plan abandonné** (cf. son bandeau SUPERSEDED).
- **Décision** : **routine Claude Code distante planifiée** (claude.ai, trigger `trig_01JtTsMm27eTAGxR5po5KmMQ`), cron `0 6 * * 1,3,5,0` (lun/mer/ven/dim 08:00 Paris), modèle **claude-sonnet-4-6**. Elle tourne dans un sandbox cloud Anthropic avec son propre checkout du repo (allowed_tools Bash/Read/Grep/Glob), **fetch JSearch (RapidAPI) via `curl`** (5 requêtes-rôles, `num_pages=1`, `country=fr`, ~87 req/mois sous le tier gratuit), score la rubric /10 + extrait 5-9 skills (flag `on_cv` vs `skill_radar`/`user_profile`) + estime le salaire, puis **lit/écrit `jobs` + `job_scans` via le connecteur MCP Supabase** (`execute_sql`). Réalise le design 2026-05-27.
- **Résolution des deux contraintes** (qui avaient motivé le faux pivot GH Actions) : (1) **pas de secret GitHub lisible par un agent distant** → la clé RapidAPI est portée **en clair dans le prompt de la routine** (config claude.ai privée) et Supabase est joint via le **connecteur MCP** (auth propre, pas de `SUPABASE_SERVICE_KEY` en env) ; (2) **pas de coût LLM récurrent** → la routine est **couverte par le plan Max** (pas de facturation par run comme l'API). Le pivot Gemini devient donc inutile — on garde Sonnet (qualité de scoring) à coût marginal nul.
- **Conséquences** : 0 €/run effectif (plan Max ; à partir du 2026-06-15, pool de crédits Agent SDK séparé mais empreinte faible). Abandon de l'**intel warm** (signaux boîte / lead / réseau / angle / maturité SAFe) et de la **reco CV** (`cv_recommended`/`cv_reason` plus écrits, cf. refonte front). `intel` jsonb = `{ salary_estimate, skills_required:[{name,on_cv}] }`, `intel_depth = 'light'`. **Détection auto de clôture supprimée** (plus de navigateur) → `closed_at` devient front-only via le bouton manuel (**renverse** la part « Cowork auto » d'ADR-17/ADR-18). Couverture élargie hors LinkedIn (liens « Postuler » parfois Indeed/WTTJ). `linkedin_job_id` stocke l'id JSearch. Match `on_cv` sans CV dans le cloud (basé sur `skill_radar`/`user_profile`). Clé RapidAPI à régénérer si elle a fuité (elle vit dans le prompt + transcripts). `pipelines.yaml` la liste sous `external_routines:` (hors timeline GHA) ; `dependencies.yaml` owner `jobs_radar_routine`.

## ADR-20 · 2026-05-28 · Jobs Radar v2.1 — exploitation des champs JSearch (remote, skills depuis l'annonce, filtre fulltime)

- **Contexte** : la routine (ADR-19) n'exploitait qu'une fraction du JSON JSearch (titre, boîte, description, ville, date, lien, salaire). Champs inutilisés à valeur : `job_is_remote` (préférence géo de Jean), `job_highlights` (`{Qualifications, Responsibilities, Benefits}` — source **structurée** des compétences, plus propre que la description brute), `job_employment_types` (filtrer le non-permanent), `employer_logo` (UX). Quota réel mesuré : **200 req/mois** (pas ~100), large marge.
- **Décision** : (1) **Filtre dur FULLTIME** avant scoring/insertion — les offres dont `job_employment_types` est renseigné et exclut FULLTIME (INTERN/PARTTIME/CONTRACTOR) sont écartées (gardées si le champ est absent). Conséquence : `employment_type` n'a **pas** de colonne (toutes les lignes sont FULLTIME). (2) **Skills depuis `job_highlights.Qualifications`/`Responsibilities` en priorité**, fallback `job_description` ; provenance tracée dans `intel.skills_source`. (3) **`job_is_remote` → colonne `jobs.is_remote boolean`** (migration `sql/016_jobs_is_remote.sql`) — badge « Remote » + filtre front ; **n'influe pas sur le score** (la géo reste gérée par le calibrage `job_pref_rules`). (4) **`employer_logo` → `intel.employer_logo`** (affichage seul, jsonb, pas de colonne).
- **Conséquences** : data contract `intel` étendu = `{ salary_estimate, skills_required:[{name,on_cv}], skills_source, employer_logo }`. Nouvelle colonne `is_remote` (lecture seule front, hors whitelist PATCH). Filtre fulltime = moins de bruit mais dépend d'un champ JSearch parfois absent (garde-fou : on garde si inconnu). Skills plus fiables quand `job_highlights` est rempli (variable selon les offres). Prompt de la routine (Étapes 1 / 1.5 / 3 / 4) mis à jour ; front (carte + filtre Remote + logo + label « d'après l'annonce ») ; `tab-jobs.md` + `dependencies.yaml` + `external_routines` à jour. `closed_at` reste front-only (inchangé vs ADR-19).

## ADR-21 · 2026-05-29 · Jobs Radar — réorientation du matching vers l'IA (requêtes + règles utilisateur)

- **Contexte** : audit du 2026-05-29 — le radar optimisait la trajectoire actuelle de Jean (RTE/PM senior → postes prestige PM/Chief of Staff) et était aveugle à son ambition déclarée (devenir expert IA, en CDI senior, potentiellement créer sa boîte). Preuves : 5 requêtes-rôles 100 % management produit/programme, **aucune requête IA** ; `ambitions`/`interests`/`what_excites_me` jamais lus par la routine ; `job_pref_rules` (clé « autorité absolue » lue à l'Étape 0) **inexistante en base** — toute la personnalisation reposait sur `job_pref_observed` (poids moindre) ; score **anti-corrélé** aux verdicts (👎 moy 8,72 > 👍 9,00 sur n=2 ; Joko CoS noté 10/10 downvoté).
- **Décision** : (1) **`user_profile.job_pref_rules` créée** — règles explicites de Jean : cap pivot IA en CDI senior ; fort bonus IA-core / apprentissage IA / scope large + exposition C-suite ; **éliminatoire** = package < 80k€ fixe **ou** < 10k€ variable, expertise verticale absente (ML eng, infra/IAM, compta, crypto/web3 pur), conseil/ESN ; secteur neutre ; remote indifférent ; **grand groupe non éliminatoire**. (2) **ÉTAPE 1 : 5 → 8 requêtes-rôles** — ajout de `AI product manager`, `AI program manager`, `head of AI product`, `generative AI product manager` ; `transformation program manager` fusionnée dans `senior program manager`. (3) **ÉTAPE 3 réorientée** : « Roles cibles » IA-first, « Secteurs chauds » IA/AI tooling/GenAI en tête, crypto/web3 déplacé en froid. Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : quota JSearch ≈ **138 req/mois** (sous le plafond 200, ADR-20). Le scoring ne **re-score pas** le stock existant (les ~315 offres `new` gardent leur ancien score — re-boucle de calibrage = chantier futur) ; `job_pref_rules` prime sur la rubric mais n'agit qu'aux scans suivants. Remote sorti des priorités (Jean = indifférent) → **backfill `is_remote` abandonné**. `pipelines.yaml` (`external_routines`) + `tab-jobs.md` + `index.json` mis à jour. Pistes non faites : refonte **rubric FIT** (axe alignement IA + faisabilité, pénalité expertise manquante, réconcilie le score avec les verdicts), **re-scoring hebdo** du stock actif, **filtres front** (stage/lieu/verdict, « masquer mes 👎 »).
- **Addendum 2026-05-29 (exécution)** : (a) **3 des requêtes IA initiales (`AI … in France`) renvoyaient 0** sur JSearch — formulations validées et corrigées : `… Paris` et le français (`product manager intelligence artificielle`) fonctionnent ; ÉTAPE 1 utilise désormais des **requêtes complètes** (plus de suffixe `in France`), 9 requêtes, ~156 req/mois. (b) **JSearch renvoie `403 Host not in allowlist` depuis le sandbox cloud** (IP datacenter rejetée par RapidAPI) → les runs cloud (cron + manuels) échouent ; le fetch ne marche que depuis une IP autorisée. Voie durable retenue : **réactiver le cloud** via l'allowlist RapidAPI (à défaut, fetch local). Un **scan IA one-shot a été lancé en local** (machine de Jean) le 2026-05-29 : 42 offres scorées selon `job_pref_rules` (21 new / 21 archived) et insérées via REST (service key).

## ADR-22 · 2026-05-31 · Jobs Radar — Engagement Manager comme rôle cible (scope tech/IA)

- **Contexte** : Jean (RTE, ex-manager PwC Digital) veut suivre les postes d'« engagement manager », alignés avec son poste actuel. - **Contexte** : `jobs_inherit_user_status` (migration 013) neutralise les republications LinkedIn en héritant du `status` archived/snoozed d'une ligne (title, company) récente. Mais il matchait **tout** `archived`, y compris les archivages **automatiques** (score < 5 au scan, sans verdict). ## ADR-24 · 2026-06-01 · Veille IA — contrainte `UNIQUE(url)` sur `articles` + ingestion idempotente

- **Contexte** : `articles` (table principale de la veille IA) était la seule table de contenu sans contrainte `UNIQUE(url)`. `main.py::save_to_supabase` postait en `Prefer: resolution=ignore-duplicates` mais sans `?on_conflict=url` ni contrainte → PostgREST résolvait les conflits sur la PK `id` (UUID toujours neuf), donc aucun dédup. Avec `LOOKBACK_HOURS=36` et un run quotidien, chaque article re-servi par un flux RSS deux jours de suite était ré-inséré. Constaté le 2026-06-01 : **244 doublons** (2030 → 1786 lignes uniques, jusqu'à 13 copies d'une même URL), visibles dans l'onglet Veille IA. Les 4 corpus satellites (anime/gaming/sport/news_articles) avaient déjà `UNIQUE(url)` → 0 doublon.

Le dédup historique est une opération MCP one-shot, non rejouable. Doc : `sql/019_articles_url_unique.sql`.

## ADR-25 · 2026-06-04 · Jobs Radar — dédup logique (employeur+titre) + sélection d'URL durable (anti-lien-mort)

- **Contexte** : des hot leads pointaient vers des liens morts — Pigment « Engagement Manager » (`applied`) sur jobintree → HTTP **410**, BForBank « AI Program Manager » (`applied`) sur trabajo.org → instable. Cause racine double : (1) le dédup (ADR-19, ÉTAPE 2) ne portait que sur `linkedin_job_id` (= `job_id` JSearch), or JSearch syndique **une même offre sous plusieurs `job_id`** selon le feed source → **2 à 4 lignes par offre** (constaté : 22 clusters dupliqués actifs, dont Pigment EM en **3 exemplaires tous `applied`**) ; (2) `url = job_apply_link` brut → souvent un agrégateur jetable (jobintree/trabajo/hugodecrypte) qui expire en quelques jours, voire un **endpoint API `jsearch.p.rapidapi.com`** non cliquable (cas Doctolib). JSearch expose pourtant `apply_options[]` (avec un flag `is_direct` = lien ATS employeur) jamais exploité.
- **Décision** : correctifs **prompt-only** (pas de migration, pas de backfill de schéma). (1) **ÉTAPE 2 — dédup LOGIQUE** : clé `(employeur normalisé + titre normalisé)` (retire H/F, `(x/f/m)`, parenthèses, ponctuation, espaces, accents) sur les offres vues ≤ 45 j ; match si `job_id` connu **ou** clé logique identique → `UPDATE last_seen_date` sans re-scorer, **+ upgrade de l'`url`** si le nouveau lien est d'un palier plus durable. **Garde-fou anti-sur-fusion** : employeur générique/masqué (`Confidential`, vide) → jamais de fusion sur titre, dédup `job_id` seul. (2) **ÉTAPE 4 — CHOIX DE L'URL** : `apply_options[].is_direct=true` (ATS) → host le plus durable (lever/greenhouse/smartrecruiters/workday/ashby/WTTJ/`*.jobs`/`careers.*` > linkedin) → agrégateur ; **rejet absolu du domaine `jsearch.p.rapidapi.com`** (fallback = lien de recherche LinkedIn). Palier tracé dans `intel.link_source` ∈ {direct, durable, aggregator, search-fallback}. Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : `intel` étendu = `{ …, link_source }` (offres existantes sans la clé — pas de backfill, champ diagnostique non lu par le front). Le dédup logique réduit fortement les lignes mais peut, en théorie, fusionner deux postes distincts au titre identique chez un même gros employeur (rare ; le garde-fou couvre les employeurs masqués ; réversible côté stock via `status`). Ne re-score pas le stock (cohérent ADR-21/22). **Nettoyage one-shot du stock** (MCP, hors routine) le 2026-06-04 : BForBank repointé vers l'ATS Crédit Agricole, Pigment EM marqué fermé (poste retiré de l'ATS Lever, 3 copies mortes), **~25 doublons archivés** (réversible : note datée + `status='new'`) ; 3 clusters laissés intacts (Euronext SPM `applied`+`new`, 2× `Confidential` — fusion jugée risquée). Blocage cloud JSearch `403` (ADR-21) **inchangé**. Doc : `pipelines.yaml` (`external_routines`, v2.4) + miroir `docs/cowork-routines/jobs-radar.md` mis à jour.

## ADR-26 · 2026-06-04 · Jobs Radar — vieillissement automatique (auto-archive des annonces non revues >30j)

- **Contexte** : sans mécanisme d'expiration, les leads `new` s'accumulent indéfiniment (332 `new` constatés le 2026-06-04, dont **120 non revus depuis >30j** — moyenne 40j, le plus vieux du 20/04). Or la routine (ADR-19, ÉTAPE 2) rafraîchit `last_seen_date` à chaque fois que JSearch renvoie encore l'offre : un `new` non revu depuis longtemps est donc une annonce **quasi certainement fermée** (futur lien mort). Le dédup logique + URL durable (ADR-25) empêche doublons et liens morts *à la création*, mais pas le **pourrissement** des offres après insertion.
- **Décision** : nouvelle **ÉTAPE 6 — Vieillissement** dans la routine (prompt-only, pas de migration) : `UPDATE jobs SET status='archived' WHERE status='new' AND last_seen_date < CURRENT_DATE - INTERVAL '30 days'`, note datée `auto-archive vieillissement` (réversible `status='new'`). **GARDE-FOU critique** : l'étape ne s'exécute QUE si le run a effectivement fetché des offres (`total_fetche > 0`) — un échec global JSearch (ex : `403` cloud, ADR-21) ne rafraîchit pas `last_seen_date` et archiverait à tort des offres vivantes. Ne touche QUE `status='new'` — jamais `applied`, `snoozed`, `user_verdict*`, `closed_at`. Tourne à chaque run (4×/sem) plutôt qu'hebdo (plus réactif ; le seuil 30j absorbe les échecs transitoires : une seule exécution réussie en 30j ré-arme `last_seen`). Appliqué au prompt **live** via `RemoteTrigger update` (miroir [docs/cowork-routines/jobs-radar.md](../cowork-routines/jobs-radar.md)).
- **Conséquences** : la vue `new` reste resserrée sur les offres réellement actives (~14j de fraîcheur). **Interaction avec ADR-23** : le trigger `jobs_inherit_user_status` hérite d'un `archived` quand `score_total >= 5` ; un lead auto-archivé à score ≥ 5 devient indistinguable d'un archivage manuel → une offre re-postée après auto-archivage ne ré-émerge pas d'elle-même (le dédup logique d'ADR-25 la matche et rafraîchit `last_seen` sans changer le statut). Jugé acceptable (rare ; toujours réversible à la main). **Cleaning one-shot** du stock le 2026-06-04 : 120 leads périmés archivés (108 sous-7 + 12 hot leads). Doc : `pipelines.yaml` (`external_routines`, v2.5) + miroir mis à jour.

## ADR-29 · 2026-07-25 · Médiathèque — le contrat de données est celui d'AniList, toute source y est traduite

**Contexte.** ADR-28 annonçait l'extension à d'autres `media_type` « sur le même schéma ». À l'arrivée de TMDB (films et séries), la question réelle n'est pas le schéma — il tenait — mais le **vocabulaire** : TMDB expose `status` au niveau série (`Returning Series`, `Ended`…), des saisons avec `episode_count`, un `next_episode_to_air` global. AniList expose `airing_status` par entrée, `episodes`, `nextAiringEpisode`. Toute la logique dérivée du front (`released`, `status`, `currentEntryOf`, `pickHero`, `buildWeek`, `pickTonight`) lit le vocabulaire AniList. Deux options : brancher chaque fonction sur la source, ou traduire à l'ingestion.

**Décision.**
1. **Le contrat de données est celui d'AniList.** Toute source nouvelle y est traduite **une fois, à l'ingestion**. `cockpit/lib/mediatheque-view.js` n'a pas été modifié d'une ligne pour accueillir TMDB — c'est le critère de réussite de la traduction, et il est vérifié par des tests dédiés dans `tests/test_tmdb_map.mjs` qui font tourner les fonctions dérivées sur des lignes TMDB.
2. **Deux règles imposées par TMDB**, dont le `status` est au niveau série : seule la **dernière** saison en hérite (les précédentes sont `FINISHED`, sinon `released()` lirait `next_episode_number - 1` sur une saison ancienne et sous-compterait ses épisodes), et `next_episode_to_air` ne s'accroche qu'à elle.
3. **`source` discrimine le namespace**, pas seulement la provenance : `tmdb_movie` / `tmdb_season` au niveau entrée, parce que les ids de films et de saisons TMDB peuvent **collider numériquement** sous `UNIQUE(source, source_id)`. Corollaire : chaque sync est **borné à sa propre source** en lecture (`franchises_qs()` / `entries_qs()`), sans quoi le sync AniList enverrait un id TMDB à AniList et écraserait la fiche.
4. **Duplication assumée du mapper** entre `cockpit/lib/tmdb.js` et `pipelines/tmdb_tracker_sync.py` — un pipeline Python ne peut pas importer un module JS, exactement comme pour le walk AniList (ADR-28, point 3). Elle n'est acceptable que testée : `tests/test_tmdb_map.py` reprend cas pour cas `tests/test_tmdb_map.mjs`.
5. **Clé TMDB stockée à deux endroits** : secret GitHub pour le pipeline, `user_profile.tmdb_api_key` pour la recherche côté front, qui ne peut pas lire un secret CI. Pattern déjà établi par `lastfm_api_key`. Pas d'Edge Function : ce serait la première du projet pour un gain nul (un seul utilisateur authentifié).

**Conséquences.** Le vocabulaire AniList (`airing_status`, `episodes_total`, `next_episode_number`) devient un **contrat inter-sources**, pas un détail d'implémentation : le renommer casserait toutes les sources d'un coup. CSP élargie (`api.themoviedb.org`, `image.tmdb.org`). Nouveau cron 07:45 UTC, décalé de 15 min pour ne pas empiler deux syncs de `media_entries`. `media_entries` et `media_releases` ont désormais **deux** pipelines propriétaires. Doublon cross-source assumé en v1 : un anime référencé aussi sur TMDB donnera deux franchises — dédupliquer demanderait une table de correspondance, jugée trop chère pour le cas.

## ADR-31 · 2026-07-28 · Jobs Radar — le quota n'est pas un paramètre à régler, c'est une contrainte à instrumenter

**Contexte.** Deuxième panne totale en un mois : du **10 au 27 juillet**, huit runs consécutifs écrivent `raw_count = 0`. Personne ne le voit pendant trois semaines, parce qu'une panne de fetch et un jour calme produisent **exactement la même ligne** `job_scans`. ADR-27 avait déjà diagnostiqué ce quota le 26/06 et l'avait traité en réglant un curseur — 4→3 runs/semaine, « conso ≈143/mois, marge ~57 ». La rechute prouve que le curseur était le mauvais levier : 143 est un *nominal*, et la moindre variance (retry d'une requête en échec, run manuel de test) le pousse au-delà de 200 sans qu'aucun signal ne l'indique.

Vérifications du 28/07, quota fraîchement remis à zéro : clé valide, `HTTP 200`, `X-RateLimit-Requests-Remaining: 199/200`, reset ≈ le 27 de chaque mois. Un run de test depuis le sandbox cloud consomme 12 requêtes et reçoit des réponses — **le `403 Host not in allowlist` d'ADR-21 ne s'applique plus**, le fetch cloud fonctionne. La cause est donc bien l'épuisement du quota, et rien d'autre.

**Décision.**
1. **Journaliser la santé du fetch en base.** `job_scans.tendances` porte désormais `{"fetch": {queries_planned, queries_ok, queries_failed, statuses, quota_limit, quota_remaining, aborted_reason, error_sample, rotation_lot}}`, écrit **même quand 100 % du fetch échoue**. C'est le vrai correctif : le défaut de fond n'était pas le quota, c'était qu'aucune trace ne distinguait la panne du silence. Aucune migration — la colonne existait, vide (`{}`), et le front ne la lit pas (`data-loader.js::transformJobScan()` recalcule ses propres `volumes_7d` / `ratios_category`).
2. **Discipline de quota explicite dans le prompt** : aucun retry sur requête en échec (un retry consomme et ne répare rien), aucune requête hors des 8 prévues, lecture de `X-RateLimit-Requests-Remaining` dès la première réponse, arrêt immédiat sur `429`.
3. **Socle + rotation, 8 requêtes/run.** 5 requêtes IA à chaque run, 3 tirées d'un lot A/B/C sélectionné par `jour_de_l_année mod 3`. Couverture portée à **14 requêtes distinctes contre 11**, pour une conso ramenée de ~143 à **~104/mois (52 % du quota)**. Les trois requêtes génériques (`product manager in France`, `delivery manager Paris`, `senior program manager in France`) passent en rotation : elles alimentaient l'essentiel du bruit — `pjm` pèse 332 offres pour un score moyen de 1.98 et **zéro candidature**. Les quatre formulations nouvelles ont été validées contre JSearch avant d'être écrites (10 résultats chacune).
4. **Le vieillissement se compte en scans réussis, pas en jours calendaires.** L'ÉTAPE 6 d'ADR-26 archivait tout lead `new` non revu depuis 30 jours ; les trois semaines de panne ont mangé ce budget sans qu'aucune offre ait eu la moindre chance d'être revue. **38 leads `new` vivants auraient été auto-archivés au premier run réussi.** Nouveau prédicat : `(SELECT count(*) FROM job_scans s WHERE s.scan_date > j.last_seen_date AND s.raw_count > 0) >= 13` — une panne ne consomme plus le budget de fraîcheur.
5. **Boucle d'apprentissage (ÉTAPE 7)**, le recalibrage hebdomadaire abandonné en v1 par ADR-19. Le lundi, si ≥3 nouveaux verdicts depuis le dernier passage, la routine réécrit `user_profile.job_pref_observed` depuis les verdicts et candidatures à 120 jours. `job_pref_rules` reste interdit d'écriture. Le seuil de 3 est essentiel : réécrire une synthèse sans signal neuf ne peut que dégrader l'existant.
6. **`intel.source_query`** conserve la requête qui a fait apparaître chaque offre, et `intel.link_source` est reverrouillé sur son vocabulaire fermé de 4 valeurs (il avait dérivé en texte libre — `'LinkedIn'`, `'apec'`, `'trabajo.org'`… sur ~35 lignes).

**Conséquences.** Le radar redevient diagnosticable sans rejouer un `curl` à la main : `SELECT tendances FROM job_scans` suffit. La marge de quota passe de ~28 % à ~48 %, et un dépassement s'auto-limite désormais au lieu de tuer le mois. **Point 6 ↔ point 3** : `source_query` est ce qui permettra, au prochain cycle, d'élaguer les requêtes stériles **sur données réelles** plutôt qu'à l'intuition — l'arbitrage socle/rotation posé ici est un pari argumenté, pas une mesure. **Limite reconnue et non corrigée** : la boucle d'apprentissage est à l'arrêt faute de carburant — dernier verdict le **2026-06-01**, zéro sur 30 jours, et la fenêtre de 90 jours que lisait l'ÉTAPE 0 (portée à 120) serait vide au 30/08. L'ÉTAPE 7 restera inerte tant que l'utilisateur ne votera pas ; aucun réglage de prompt ne compense l'absence de signal. **Ce qui n'est pas traité** : le plafond de 200 req/mois reste structurel — une seconde source (France Travail, API publique et gratuite) ou un plan payant sont les seules sorties par le haut, laissées à l'arbitrage utilisateur.

## ADR-32 · 2026-07-29 · Jobs Radar — « ai-je déjà vu cette offre ? » n'a pas de date de péremption

**Contexte.** Symptôme utilisateur : *« j'ai souvent des offres qui ressortent pour lesquelles les candidatures ne sont plus acceptées »* (ex. Engagement Manager chez Postman). Trois défauts indépendants s'additionnaient, et aucun n'était visible isolément.

1. **La fenêtre de dédup.** ADR-25 dédoublonne sur une clé logique, mais la routine ne chargeait l'historique que sur `last_seen_date >= CURRENT_DATE - 45 days` — **365 lignes sur 1889**. Postman : vue le 2026-05-31, `last_seen` figé au 2026-06-12, re-fetchée le 2026-07-28. **46 jours.** Ratée d'un jour, réinsérée comme lead neuf à 7.0. Le fenêtrage était le mauvais outil : la question « ai-je déjà vu cette offre ? » n'a pas de date de péremption, contrairement à « cette offre est-elle encore en ligne ? ».
2. **Deux normalisations divergentes.** La routine fusionnait « Product Manager H/F » et « Product Manager (H/F) » ; le trigger `jobs_inherit_user_status` (013/018), lui, matchait sur `(lower(title), lower(company))` **exact** et les voyait comme deux offres distinctes. Le filet de sécurité ne rattrapait donc pas ce que la dédup laissait passer.
3. **Le trigger ignorait `closed_at`.** Le bouton « Marquer clôturée » (ADR-18) n'écrit **que** `closed_at`, sans toucher au `status`. Une republication ne matchait rien et renaissait avec `closed_at = NULL` : l'offre explicitement déclarée morte revenait, l'air neuve. C'est le cœur du symptôme.

**Contrainte externe, vérifiée.** JSearch n'expose **aucun** champ d'expiration (35 champs inspectés le 2026-07-29 : pas de `job_offer_expiration_*`), et LinkedIn republie des annonces mortes avec un `job_posted_at` rafraîchi — Postman ressortait daté « il y a 6 jours ». **Il n'existe aucun signal externe de clôture.** La seule information fiable est la décision de l'utilisateur, et le système doit donc cesser de la perdre. C'est ce qui rend le point 3 structurant plutôt que cosmétique.

**Décision.** Migration `sql/026_jobs_logical_key.sql`.
1. **La normalisation devient du code, à un seul endroit** : `jobs_logical_key(company, title)`, `IMMUTABLE` (d'où `translate()` pour les accents plutôt que `unaccent()`, seulement `STABLE`). Elle retire les parenthèses et les mentions de genre **avant** la ponctuation — sinon « H/F » survivrait en `hf` et casserait l'égalité des clés. Validée sur 11 cas, dont `AI/ML` qui ne doit **pas** être mangé par le filtre de genre, et l'exemple `bforbank|aiprogrammanager` d'ADR-25 reproduit à l'identique.
2. **Colonne générée `jobs.logical_key` + index.** La routine interroge désormais l'historique complet en une requête `JOIN ... ON j.logical_key = jobs_logical_key(v.company, v.title)`, **sans fenêtre temporelle**, et ne calcule plus la clé elle-même : une seconde implémentation redivergerait du trigger.
3. **Le trigger hérite `closed_at` sans péremption** et hérite `applied` (jamais inhérité jusqu'ici : une offre à laquelle on avait candidaté revenait en `new`). Fenêtres élargies 30j→90j (`archived`) et 7j→14j (`snoozed`).
4. **Les auto-archivages sont exclus de l'héritage** via le marqueur `auto-archive vieillissement` de `user_notes`. ADR-23 distinguait « décision user » de « archivage auto » par `score_total >= 5` ; ADR-26/31 a rendu cette heuristique fausse, le vieillissement produisant justement des `archived` à score ≥ 5. L'intention d'ADR-23 est ainsi restaurée — le libellé du marqueur devient un contrat entre l'ÉTAPE 6 de la routine et le trigger.

**Vérification.** Quatre republications simulées en transaction annulée : Postman `Engagement Manager (H/F)` → `applied` (décision retrouvée malgré une orthographe différente) ; Scaleway clôturée **68 jours** plus tôt → `archived` + `closed_at` restauré ; boîte inconnue → `new` (pas de sur-blocage) ; `Confidential` → `new` (garde-fou anti-sur-fusion d'ADR-25 intact). **220 doublons latents** mesurés sur 1892 lignes (11,6 %), dont 4 actifs dans le radar — fusionnés le jour même, réversibles, dont deux offres chez **Alan** et **Decathlon Digital** auxquelles l'utilisateur avait déjà candidaté et qui étaient revenues en `new`.

**Conséquences.** Une offre connue ne peut plus revenir en `new`, quel que soit le délai ou le nombre de republications. **Contrepartie assumée** : un poste réellement rouvert des mois plus tard chez le même employeur sous le même intitulé restera archivé — jugé très largement préférable au symptôme inverse, et réversible à la main. `logical_key` étant une colonne **générée**, toute tentative d'écriture par la routine ferait échouer l'INSERT (consigne ajoutée à l'ÉTAPE 4). **Découverte annexe non traitée** : le Jobs Radar est **absent de `pipeline_health`** (migration 023) — 15 pipelines y sont déclarés, pas lui. La table définit pourtant un statut `stale` (« les runs passent mais la donnée ne bouge plus ») qui décrit exactement la panne d'ADR-31 : la surface d'alerte existait, le radar n'y était pas branché. À faire.

## ADR-33 · 2026-07-29 · Jobs Radar — une calibration qui commente n'est pas une calibration

**Contexte.** Question de l'utilisateur : *« ce serait pas possible que le script analyse ce que j'ai liké + mes coms et en déduise les typologies d'offres que j'aime ? »* Le mécanisme existait déjà — `user_profile.job_pref_observed`, dérivé des verdicts, injecté dans chaque prompt de scoring, et dont ADR-31 venait de rétablir le rafraîchissement hebdomadaire. La vraie question était donc : **est-ce qu'il sert à quelque chose ?**

Mesure. Les 17 verdicts sont **tous commentés** (17/17 `user_verdict_reason` renseignés) — un signal d'excellente qualité malgré le faible volume. Et il révèle un écart structurel : **les 15 rejets portent tous sur des offres notées 7.5 à 10** (Joko CoS notée 10.0 → « Requires tier 1 strategy consulting » ; LSEG 8.5 → « Je ne suis pas ML engineer. Je ne vais rien apporter. » ; Kaino 8.5 → « trop junior, j'ai trop d'expérience »). **La rubric mesure la qualité du POSTE ; l'utilisateur juge sa CRÉDIBILITÉ dessus.** Dix rejets sur quinze disent la même chose : l'expertise verticale manque.

La calibration tournait pourtant : **27 offres sur 27** du lot du 28/07 portaient une clé `calibrage`. Mais elle se contentait de constater. Cas décisif : `Technical Program Manager, AI Delivery for Public Sector & Defense` chez Cohere, calibrage = « Technical PgM public/défense **résonne avec rejet Mistral TPM. Score ajusté.** » → **8.0, statut `new`**. Le motif de rejet est identifié, nommé, et le score ne bouge pas. Un second cas (`Senior Air Programme Manager – Defence AI`, 7.0) sort au-dessus du seuil dans un secteur que le prompt lui-même déclare froid. La consigne en cause : *« baisse sector/impact et explique dans la clé calibrage »* — **aucun montant, aucun plancher, aucun veto.** Purement advisory, donc noyé dans le bruit du scoring.

**Décision.** `job_pref_observed` cesse d'être une synthèse en prose et devient une **table de pénalités chiffrées**, chaque ligne portant un montant numérique ou le mot `VETO`, et **citant le verbatim** de l'utilisateur qui la justifie : `VETO` (score plafonné à 2.0 + `archived`) sur expertise verticale absente que `job_pref_rules` déclare déjà éliminatoire ; −2.5 TPM / JD attendant un profil d'ingénieur ; −2.0 rôle hors périmètre produit/programme/CoS ; −2.0 défense ; −1.5 pedigree conseil tier-1 ; −1.5 scope réel sous la séniorité ; −1.0 salaire estimé < 90k ou infra/middleware sans exposition produit ; +1.0 scale-up très tech à scope large avec exposition C-suite (les deux seuls votes positifs). L'ÉTAPE 3 devient impérative et cumulative, et **doit nommer chaque montant** dans `rubric_justif.calibrage` — une clé sans chiffre signifie que le test n'a pas été fait. L'ÉTAPE 7 doit **préserver ce format** en réécrivant, ajouter une ligne pour tout motif répété ≥2 fois et retirer celles qui ne se reproduisent plus sur 120 jours.

**Conséquences.** Le veto n'invente rien : il **applique** une règle que `job_pref_rules` déclarait déjà éliminatoire et que le scoring ignorait — l'« autorité absolue » n'en était pas une. Le radar deviendra nettement plus sélectif ; les montants sont un point de départ argumenté, pas une vérité, et l'ÉTAPE 7 est précisément ce qui doit les corriger à mesure que les verdicts arrivent. **Backfill du stock, le jour même.** La routine ne re-score jamais une offre connue : la grille ne se serait appliquée qu'aux offres futures, laissant 93 leads notés sous l'ancien régime. Passe manuelle via MCP sur les seuls `status='new'` — `applied` et `snoozed` intouchés — **34 offres ajustées, dont 28 archivées** : 13 `VETO` (9 conseil/ESN/cabinet de recrutement/freelance, 4 expertise verticale — cybersécurité ×2, tokenisation, data platform engineering) et 15 sous le seuil après pénalités cumulées. Chaque ligne porte son motif chiffré dans `rubric_justif.calibrage` et une note `user_notes` réversible. Résultat : **93 → 65 leads**, score moyen 6.86. Le bonus `+1.0` n'a **pas** été appliqué rétroactivement — gonfler des scores existants aurait faussé le compteur de hot leads sans rien apporter au tri. Constat au passage : neuf offres de conseil/ESN étaient classées `new` alors que `job_pref_rules` les déclare éliminatoires depuis le 2026-05-29, l'une portant même la mention « schéma conseil malgré branding IA » écrite par le scoring lui-même — la démonstration que l'« autorité absolue » ne l'était pas. **Dépendance non résolue** : ce dispositif ne s'auto-corrige que si l'utilisateur vote — dernier verdict le 2026-06-01, et l'ÉTAPE 7 exige 3 verdicts neufs pour se déclencher. Sans cela, la table restera figée sur n=17.

## ADR-34 · 2026-08-13 · Tracker jeux — tables `game_*` dédiées plutôt que réutilisation de `media_*`

**Contexte.** La médiathèque (ADR-29) a posé un contrat de données commun pour toute source ajoutée « sur le même schéma » — anime (AniList) puis films/séries (TMDB) partagent aujourd'hui `media_franchises` / `media_entries` / `media_progress` / `media_releases`, traduits au vocabulaire AniList à l'ingestion. Le tracker jeux (IGDB) se posait la même question : nouvelles tables `game_*`, ou cinquième source dans `media_*` ?

**Décision.**
1. **Tables dédiées.** `sql/027_game_tracker.sql` crée `game_franchises` (9 colonnes), `game_titles` (19), `game_progress` (7) et `game_releases` (8), RLS `authenticated` sur les 4 opérations — même pattern que `sql/020_media_tracker.sql`. L'alternative rejetée était la cinquième source `media_*` (`source = 'igdb_game'`), symétrique à ADR-29.
2. **L'argument est le critère de réussite d'ADR-29 lui-même** : « `cockpit/lib/mediatheque-view.js` n'a pas été modifié d'une ligne » y est posé comme preuve que la traduction à l'ingestion fonctionne. Un jeu n'a ni épisodes ni diffusion — `episodes_total`, `airing_status`, `next_episode_airing_at` n'ont pas d'équivalent côté IGDB, et la seule traduction plausible (`episodes_total = null` partout, `airing_status` toujours `FINISHED` ou dérivé d'un statut `early_access`/`cancelled` qui n'a pas de sens dans ce vocabulaire) aurait forcé les six fonctions dérivées testées (`released`, `status`, `currentEntryOf`, `pickHero`, `buildWeek`, `pickTonight`) à exclure explicitement les jeux à chaque appel — soit le contraire du bénéfice recherché par le contrat commun.
3. **Coût accepté** : ~40 lignes de SQL en plus (4 `CREATE TABLE` + policies), contre zéro branche défensive dans six fonctions déjà en production sur deux sources.
4. **Recherche front du lot 2 : proxy Edge Function, pas de clé en base.** IGDB refuse le CORS navigateur (contrairement à TMDB, ADR-29 point 5), donc le pattern `user_profile.tmdb_api_key` / `lastfm_api_key` ne s'applique pas ici — un `client_credentials` OAuth Twitch ne peut de toute façon pas être exposé côté navigateur. Une Edge Function `igdb-proxy` sera nécessaire au lot 2, avec `Deno.env.get()` pour le secret et `verify_jwt: true` — **rappel** : l'Edge Function `jsearch-proxy` a été supprimée le 2026-08-13 précisément pour l'anti-pattern inverse (clé RapidAPI en dur dans le source + `verify_jwt: false`, cf. `docs/secrets.md`). Ne pas reproduire.

**Conséquences.** `game_progress` reste, comme `media_progress`, une table strictement user-owned : `igdb_tracker_sync.py` n'y écrit que via `import_wishlist()` (one-shot Task 6, `ignore_dupes`), jamais ailleurs. Le lot 1 se limite à l'encart `<GamesBriefCard>` du Brief (Tier 1, `game_releases` non acquittés < 30j) — la refonte de l'onglet Gaming (lecture des 4 tables, statuts, rail « À venir ») est conditionnée à la sonde de survie télémétrie (`games_brief_shown` / `games_release_ack` / `games_unwatch_franchise`, cf. `docs/telemetry.md`) : trois semaines sans acquittement ni désabonnement après le premier événement détecté ⇒ le lot 2 n'est pas lancé et l'encart est retiré. `gaming_wishlist` (8 lignes) n'est pas supprimée — seul son usage front a disparu, absorbé dans `game_progress`.

## ADR-35 · 2026-08-13 · Tracker jeux — le lot 2 est lancé sans attendre la sonde de survie du lot 1

**Contexte.** ADR-34 conditionnait explicitement la refonte de l'onglet Gaming (lot 2) à une sonde de survie télémétrie sur l'encart `<GamesBriefCard>` du Brief : trois semaines sans un seul `games_release_ack` ni `games_unwatch_franchise` après le premier événement détecté ⇒ le lot 2 n'est pas lancé et l'encart est retiré. Le lot 1 a été livré le 2026-08-13 (secrets Twitch posés à 12:35 UTC, premier run réussi du pipeline, 451 titres en base dont 86 rattachés à un jeu Steam, 24 licences surveillées). Le même jour, avant même que la fenêtre de trois semaines ait pu commencer à produire un signal exploitable, l'utilisateur a demandé la refonte de l'onglet — en disant explicitement ne rien voir de l'encart, alors qu'il consulte le Brief quotidiennement.

**Décision.** Le lot 2 est lancé le 2026-08-13, sur décision explicite de l'utilisateur, sans attendre l'échéance posée par ADR-34. L'alternative écartée était de tenir le délai tel qu'écrit — répondre à la demande en renvoyant vers la sonde déjà en place et attendre les trois semaines. Elle a été jugée inadaptée au signal réel obtenu : la sonde mesure un taux d'interaction avec l'encart (acquittement / désabonnement), mais l'utilisateur rapporte ne pas avoir *vu* l'encart lui-même — la mesure d'usage n'a donc jamais eu l'occasion de démarrer, et attendre trois semaines de plus n'aurait rien changé à ce défaut. La leçon à retenir n'est pas que la sonde de survie était un mauvais principe — elle reste la bonne discipline pour trancher un usage réel une fois qu'une fonctionnalité est vue — mais qu'un encart de trois lignes greffé au-dessus du hero d'une page d'accueil n'a pas suffi à rendre une fonctionnalité perceptible pour son propre commanditaire. La perception d'existence est une condition préalable à toute mesure d'usage ; elle ne peut pas être supposée acquise du seul fait qu'un composant est monté et rendu à l'écran.

**Conséquences.** Le lot 2 est construit sans qu'aucune donnée d'usage réel de l'encart n'ait eu le temps de s'accumuler — le pari repose sur la demande explicite de l'utilisateur, pas sur la télémétrie. Les compteurs `games_release_ack` / `games_unwatch_franchise` posés par le lot 1 restent en place et continuent d'être émis (cf. `docs/telemetry.md`), mais leur verdict à trois semaines ne tranchera plus rien pour la décision qu'ADR-34 leur avait confiée. La sonde de survie du lot 2 lui-même (`games_status_set`, déjà documentée dans `docs/telemetry.md`) porte donc seule la charge de vérifier, cette fois à l'intérieur de l'onglet que l'utilisateur dit effectivement regarder, si la bibliothèque à statuts trouve un usage. Coût accepté : si le lot 2 ne trouve pas preneur non plus, il ne sera pas possible de démêler a posteriori un manque d'intérêt réel d'un nouveau défaut de perception — le précédent de l'encart ne peut pas être neutralisé rétroactivement. Constat à généraliser au reste du cockpit : un encart isolé sur une page d'accueil est une hypothèse de visibilité, pas une preuve ; les autres sondes de survie adossées à un encart unique (Médiathèque PWA, bande vocabulaire japonais anime, cf. `docs/specs/tab-mediatheque.md`) restent valides tant que rien n'indique qu'elles souffrent du même défaut, mais ce précédent est le premier à l'avoir confirmé empiriquement dans ce cockpit.


## ADR-36 · 2026-08-14 · Tracker jeux — le front devient un second producteur de `game_releases`

**Contexte.** Le pipeline `igdb_tracker_sync.py` ne parcourt les collections IGDB qu'à 08:30 UTC. Entre le moment où l'utilisateur commence à suivre une licence — en ajoutant un jeu console, ou en cochant « m'avertir des prochaines sorties » — et ce parcours, la licence n'a strictement aucun événement en base : le rail « À venir » reste vide alors que l'utilisateur vient précisément de demander à être averti. Constaté le 2026-08-14 : Fire Emblem: Three Houses ajouté à la bibliothèque, aucune trace de *Fortune's Weave* (17 sept. 2026) jusqu'au lendemain. Diagnostic initial « pas un bug, le cron n'a pas encore tourné » — techniquement exact, mais l'onglet promet un rail de sorties et ne le tient qu'après un délai muet pouvant aller jusqu'à 24 h. Rien à l'écran ne distingue « cette licence n'a pas de suite annoncée » de « on ne le sait pas encore ».

**Décision.** Le front écrit lui-même les événements « À venir » de la licence qu'on vient de suivre, sans attendre le cron : `syncFranchiseUpcoming()` interroge l'Edge Function `igdb-proxy` en mode `?collection=<id>`, retient les titres pas encore sortis et les insère dans `game_titles` puis `game_releases`. `game_releases` a donc désormais deux producteurs. L'alternative écartée était de laisser le pipeline seul producteur et de signaler l'attente à l'écran (« licence suivie — prochaine vérification cette nuit ») : honnête, mais elle transforme un défaut en fonctionnalité affichée et laisse l'utilisateur devant un écran vide au moment exact où son intérêt est le plus fort. Trois garde-fous bornent le second producteur : il n'agit que sur une licence `watched` rattachée à une collection IGDB et **jamais parcourue** (`bootstrapped_at` vide) — donc uniquement là où le pipeline n'a rien à dire encore ; il écrit en `resolution=ignore-duplicates` sur `UNIQUE (title_id, event_type)`, ce qui interdit de ressusciter un événement déjà acquitté ; et il ne pose **jamais** `bootstrapped_at`, tampon qui signifie « collection parcourue en entier » et qui reste la propriété exclusive de la phase B.

**Conséquences.** La règle qui décide ce qui est « à venir » existe maintenant en deux exemplaires : `pipelines/igdb_map.py::is_upcoming()` et `cockpit/lib/games-view.js::isUpcoming()`. C'est le coût accepté de la décision — le front ne peut pas importer un module Python, et déporter la règle dans l'Edge Function l'aurait rendue intestable sous node. Les deux implémentations sont verrouillées par les **mêmes cas de test** (`tests/test_igdb_map.py`, `tests/test_games_view.mjs`), y compris le libellé exact « À venir : » dont dépend l'idempotence entre les deux producteurs : un libellé qui divergerait ne créerait pas de doublon (la clé d'unicité porte sur `title_id, event_type`) mais ferait afficher au rail un texte différent selon qui a écrit le premier. Si l'une des deux règles change sans l'autre, les tests ne le verront pas — ils testent chaque côté isolément, pas leur égalité. Risque assumé, borné par le commentaire croisé porté par les deux fichiers. Second coût : l'Edge Function passe d'un usage (recherche à la demande) à deux, donc davantage d'appels IGDB ; le quota est de 4 req/s et chaque sweep coûte une requête, ce qui reste sans commune mesure avec la limite. Enfin, `docs/architecture/dependencies.yaml` liste désormais le panel Gaming comme producteur d'INSERT sur `game_releases`, et plus seulement de PATCH `acknowledged`.

**Trouvaille de sécurité en marge.** Vérifier l'Edge Function en live après déploiement a révélé que `verify_jwt: true` ne fait pas ce que `docs/secrets.md` lui prêtait : il valide la *signature* du jeton, pas la qualité de l'appelant. La publishable key du projet — publique, en dur dans `cockpit/lib/supabase.js`, dans un dépôt public — passait le filtre et suffisait à obtenir une réponse complète. Portée réelle limitée (aucune clé en dur dans la fonction, aucune écriture en base, aucun quota mensuel à épuiser — contrairement à `jsearch-proxy`), mais c'était une porte ouverte sur le quota IGDB. La fonction contrôle désormais elle-même le rôle du jeton et refuse en 403 ce qui n'est pas `authenticated`. La leçon dépasse ce cas : la doctrine « Edge Function ⇒ `verify_jwt: true` » posée après `jsearch-proxy` était une demi-mesure présentée comme une garantie, et c'est un test en conditions réelles — pas une relecture de code — qui l'a montré.


## ADR-37 · 2026-08-15 · Sécurité — fermeture de l'écriture anonyme, des RPC SECURITY DEFINER, et première sauvegarde

**Contexte.** Un audit du cockpit mené le 2026-08-15 (5 sondes produit + vérification adversariale + critique de complétude) n'a produit **aucun** constat de sécurité sur ses cinq sondes fonctionnelles ; c'est l'agent chargé de critiquer l'audit lui-même qui a trouvé les trois trous ci-dessous. (1) Trois policies étaient déclarées `roles={public}` sur une commande d'écriture — `jobs_user_update` (UPDATE), `rte_articles_insert`, `rte_articles_delete`. `public` couvre `anon`, et la clé qui active `anon` est publiable par construction (`cockpit/lib/supabase.js:6`, dépôt public) : n'importe qui pouvait modifier les 2 073 lignes de `jobs` — statuts de candidature et notes saisis à la main — et vider `rte_articles`. ADR-19 assumait `using(true)` sur `jobs`/`job_scans` pour la **lecture** par la routine distante ; l'écriture n'était couverte par aucune décision. (2) Cinq fonctions `SECURITY DEFINER` étaient exécutables par `anon`, dont `match_memories`, qui contourne par construction la RLS de `sql/006` et n'a aucune borne sur `match_threshold` ni `match_count` : appelée avec `threshold=-1, match_count=100000`, elle rend les 951 lignes de `memories_vectors` — profil de carrière, `business_ideas`, `profile_facts` en texte clair dans `chunk_text`. Signalé par le linter Supabase `anon_security_definer_function_executable`. (3) Aucune sauvegarde n'existait : 26 workflows, zéro `pg_dump`/`backup`/`export`, pour quatre mois de données dont la seule partie irremplaçable est précisément celle que l'utilisateur a saisie à la main.

**Décision.** Trois migrations (`sql/028`, `sql/029`) et un pipeline. (1) `jobs_user_update` passe `to authenticated` ; les policies d'écriture `public` de `rte_articles` sont supprimées et sa lecture passe `to authenticated` (aucun consommateur front : `grep -rn "rte_articles" cockpit/` ne renvoie rien). Les GRANT de table `insert, update, delete` **et** `truncate, references, trigger` sont retirés à `anon` sur `jobs`, `job_scans` et `rte_articles` — TRUNCATE mérite une mention à part : il n'est **pas** soumis à la row-level security, aucune policy ne le filtre, et le défaut Supabase (`grant all ... to anon`) l'accordait. Il n'est pas atteignable via PostgREST aujourd'hui, donc l'exposition était théorique, mais elle cesserait de l'être au premier chemin d'exécution SQL exposé. (2) `match_memories` est révoquée pour `anon` **et** `authenticated`, et re-grantée au seul `service_role` : `docs/specs/tab-jarvis.md:95` établit qu'elle n'est pas lue par le front, son unique appelant étant `jarvis/retriever.py:44` qui s'authentifie en service_role. `music_discoveries`, `get_stack_stats` et `get_gemini_usage_stats` **sont** appelées par le front (`data-loader.js:1301`, `:4672`, `:4674`) : révoquées pour `anon` seulement. Point technique qui rend le geste non trivial — Postgres accorde `EXECUTE` à `PUBLIC` par défaut à la création d'une fonction, donc `revoke ... from anon` seul ne retire **rien** ; il faut révoquer à `PUBLIC` puis re-granter aux rôles légitimes, ce que fait `sql/029`. `log_user_profile_change` est traitée à part : c'est une fonction de trigger, PostgREST ne l'expose pas en RPC et Postgres ne vérifie pas `EXECUTE` au déclenchement d'un trigger — la révoquer n'aurait apporté aucune sécurité tout en risquant de casser l'écriture de `user_profile`. Seul son `search_path` mutable est corrigé, comme sur les quatre autres. (3) Nouveau pipeline `backup_supabase` (hebdomadaire, dimanche 04:00 UTC) : périmètre restreint aux 22 tables qu'aucun pipeline ne sait refabriquer, sortie en artefact de run conservé 90 jours. Transport **PostgREST et non `pg_dump`**, faute de mot de passe Postgres dans les secrets du dépôt — le choix évite d'en créer un nouveau et supprime le risque de mismatch de version `pg_dump`. Côté front, le joker `https://*.trycloudflare.com` et `http://localhost:8765` sortent de `connect-src` dans les deux pages d'entrée (le tunnel Jarvis correspondant est mort depuis le 2026-04-07, cf. `user_profile.jarvis_tunnel_url`), et les trois `<script>` CDN sans contrôle d'intégrité — `supabase-js`, `dompurify`, `marked` — reçoivent un `integrity`/`crossorigin`, `supabase-js` étant au passage épinglé de `@2` (flottant) à `@2.112.3`.

**Conséquences.** La lecture de `jobs` et `job_scans` **reste ouverte à `public`** : c'est un arbitrage laissé ouvert, pas un oubli. ADR-19 la justifie par la routine distante, mais celle-ci passe en réalité par le connecteur MCP Supabase (`execute_sql`), donc en dehors de PostgREST et de la RLS — la policy de lecture publique n'a probablement plus d'utilité et pourrait être refermée, ce qui supprimerait la lecture anonyme des 2 073 offres et de leurs statuts. À trancher séparément. Deuxième reste : les clés JWT legacy du projet, dont une `anon` valide jusqu'en 2036, sont toujours actives et présentes dans l'historique git (commit `ca45b88`) ; leur désactivation se fait dans les réglages API du projet Supabase et **n'a pas pu être faite depuis le dépôt** — tant qu'elle ne l'est pas, révoquer la publishable key ne suffirait pas. Troisième reste : le défaut `grant all ... to anon` s'applique aux ~70 tables du schéma, pas seulement aux trois traitées ici ; ce qui protège les autres est leur RLS `authenticated`, sauf pour TRUNCATE qu'aucune policy ne filtre. Étendre le `revoke` à tout le schéma est le geste cohérent, laissé hors de cette décision parce qu'il touche 70 tables d'un coup. Enfin, deux tests verrouillent les régressions : `tests/test_cdn_integrity.mjs` refuse tout `<script>` distant sans `integrity` + `crossorigin`, toute version flottante, et toute réapparition du joker tunnel dans la CSP ; `tests/test_backup_supabase.py` verrouille la pagination triée de la sauvegarde et le fait qu'une erreur HTTP remonte au lieu de produire un dump partiel qui se croirait complet — le même défaut que celui relevé sur `weekly_analysis`. Le SRI de `supabase-js` est le point de fragilité du lot : une empreinte fausse empêcherait le client Supabase de se charger et casserait l'application entière, ce qui ne se vérifie qu'en prod.


## ADR-38 · 2026-08-17 · Observabilité — un run qui ne produit rien doit échouer, et l'alerte doit sortir du cockpit

**Contexte.** Entre le 2026-07-12 et le 2026-08-16, les cinq runs dominicaux de `weekly_analysis` ont affiché un coche vert dans GitHub Actions en n'écrivant strictement rien : `learning_recommendations` et `weekly_challenges` figées au 06/07, `weekly_opportunities` à zéro, et en base `tokens_used = {"calls":0,"cost_usd":0.0}`. L'audit du 2026-08-15 avait listé quatre causes possibles (401, 403, 429, ou un 404 sur le model id) en concluant que le code les rendait indistinguables. Les logs GitHub Actions tranchent, et aucune des quatre n'était la bonne : **HTTP 400 `invalid_request_error` — « Your credit balance is too low to access the Anthropic API »**, sept fois par run, identique le 19/07 et le 16/08. Le model id `claude-haiku-4-5-20251001` est valide et le modèle est actif ; il n'a jamais été en cause. Trois défauts distincts ont concouru à masquer la panne pendant cinq semaines. (1) `call_claude` renvoyait `None` sur toute réponse non-200 sans distinguer un refus définitif d'un incident transitoire, donc le run enchaînait ses 7 appels alors que le premier avait déjà tranché ; `tracker.calls` ne comptant que les succès, la base enregistrait `calls: 0` — ce qui se lisait « n'a rien tenté » alors que le pipeline essayait bien chaque dimanche. (2) `main()` ne propageait aucun code de sortie. (3) Le seul canal d'alerte, le bandeau `PipelineHealthBanner` livré le 2026-07-26, filtre par `pipeline_health.panels` — or les panels de `weekly_analysis` sont `recos`, `challenges`, `opps` et `signals`, à zéro ouverture depuis le 28 avril. L'alerte était enfermée dans les onglets que la panne avait fait déserter. Trois constats connexes du même audit relèvent du même défaut de visibilité : `feedparser` ne lève jamais d'exception sur un flux mort (404, 410, redirection HTML) — il renvoie `bozo=1` et `entries=[]`, ce qui rend le `try/except` de `main.py` inatteignable pour le cas le plus fréquent et a laissé **16 des 43 sources RSS** muettes sans un mot ; `section_opened` n'était émis que depuis `handleNavigate`, donc jamais pour l'écran d'atterrissage ni pour la PWA Médiathèque ; et aucun des 26 workflows n'avait de job `if: failure()`.

**Décision.** (1) **`weekly_analysis` échoue bruyamment** : une fonction `is_fatal_api_error(status, body)` classe les refus — 401, 403, 400 portant « credit balance » et 404 portant « model » sont définitifs et annulent les étapes restantes via `CostTracker.fatal`, tandis que 429 et 5xx restent transitoires et laissent le run continuer. Un 400 ordinaire (prompt trop long, `max_tokens` invalide) reste volontairement local à l'appel : il ne doit pas annuler des étapes dont les prompts diffèrent. `run_exit_code(tracker)` rend 1 si aucun appel n'a réussi **ou** si un refus définitif est survenu, et `main()` le propage. (2) **L'alerte hors cockpit vit dans `pipeline_health`**, pas dans un hook `if: failure()` par workflow. C'est le point décisif de cette décision : un hook d'échec ne voit que les runs rouges, or la panne qui s'est cachée cinq semaines sortait **verte** — seul le statut `stale`, calculé par `pipeline_health` en comparant la fraîcheur de la table de sortie, la voyait. Le script tient donc à jour **une** issue GitHub dont le corps est réécrit à chaque passage (le cron est quotidien : commenter produirait ~365 notifications par an et l'alerte serait muette par saturation) et qui se ferme d'elle-même au retour au vert. (3) **Le Brief porte toutes les pannes**, les autres onglets gardent le filtrage contextuel — un bandeau Strava sur l'onglet Musique serait du bruit. (4) **Les flux RSS morts sont détectés explicitement** (`feed_failure()` teste `status` et `entries`) avec un **cliquet** : la constante `MAX_DEAD_FEEDS = 16` fixe le socle mesuré le 2026-08-17 et le run échoue dès qu'un flux de plus meurt. Faire échouer sur les 16 actuels aurait rendu le brief quotidien rouge en permanence pour une dette déjà identifiée, et noyé le signal. (5) **`section_opened` est émis depuis un effet sur `[activePanel]`** avec un champ `entry` ∈ {`landing`, `nav`, `pwa`, `pwa-resume`}, et `boot-mediatheque.js` l'émet enfin.

**Conséquences.** Le correctif de code **ne restaure pas** le pilier Apprentissage : il rend la panne visible, la cause est un compte Anthropic sans crédit et seule une recharge y remédie. Le mode Cloud de Jarvis (`jarvis/config.py`, `jarvis/server.py`) partage la même clé et est mort de la même cause — ce que l'audit avait attribué à un désintérêt. Découverte en marge, qui invalide une partie d'ADR-37 : **les permissions par défaut du dépôt sont `read`**, donc le `gh issue create` ajouté la veille au workflow de sauvegarde aurait échoué en 403 ; `backup-supabase.yml` et `pipeline-health.yml` déclarent désormais `issues: write` explicitement. Deux dettes restent ouvertes et assumées : les **16 flux RSS morts** ne sont pas réparés, seulement chiffrés — la section `energy` est morte en entier et mérite probablement une suppression plutôt qu'une réparation ; et la **télémétrie antérieure au 2026-08-17 reste inexploitable** pour comparer des onglets entre eux, ce que `docs/telemetry.md` documente désormais explicitement. Enfin, `MAX_DEAD_FEEDS` est un cliquet, pas un seuil de qualité : réparer ou retirer un flux doit s'accompagner d'une baisse de la constante, sans quoi le garde-fou se relâche silencieusement.


## ADR-39 · 2026-08-17 · Jobs Radar — l'écart de compétences que le marché renvoie, et la boucle de relance

**Contexte.** L'audit du 2026-08-15 a établi que Jobs Radar instrumente tout l'amont — 2 073 offres scorées, 73 scans, une rubrique calibrée — puis s'arrête net au moment où l'enjeu commence. Deux gisements dormaient. (1) La routine extrait à chaque scan, offre par offre, les compétences exigées avec un drapeau `on_cv` (ADR-19/20) : 2 156 paires sur 551 offres, affichées carte par carte par `JrSkills` et **jamais agrégées**. (2) Le calcul des candidatures en souffrance existait déjà dans `data-loader.js`, mais le bouton qui l'affichait n'avait **aucun `onClick`** — 30 candidatures sur 32 dépassaient dix jours sans relance, la plus ancienne remontant au 2026-04-28. Trois défauts annexes aggravaient le second point : le plafond `.slice(0, 2)` rendait la file invidable, le libellé annonçait « candidaté il y a N j » à partir de `last_seen_date` (qui est la dernière re-parution de l'offre chez JSearch, pas une date de candidature), et le schéma `job_scans.actions` écrit par la routine (`{note, job_id, company, priority}`) divergeait de celui que lit le panel (`{id, kind, label, cta}`) — quand la routine produisait vraiment des actions, les lignes se rendaient vides. Enfin, le panel ne chargeait que 300 offres triées par score, laissant 55 offres `new` — dont des offres du jour — invisibles derrière des archivées mieux notées, avec un seuil de coupure qui monte tout seul à mesure que la base grossit.

**Décision.** (1) **Une vue SQL `market_skill_gap`** (`sql/031`) plutôt qu'un calcul client : l'agrégat déroule 2 156 paires. La normalisation se fait **par règles, pas par table d'alias** — mesuré le 2026-08-17, il y a 1 282 libellés distincts pour 849 manques et **627 de ces libellés n'apparaissent qu'une seule fois** (73 %) ; une table d'alias ligne à ligne n'aurait jamais été tenue à jour. Les règles regroupent les axes porteurs et laissent le reste tel quel, avec une liste noire pour les artefacts de parsing (titres de section de l'annonce, et un identifiant de tracking de job board — `#j-18808-ljbffr`, 5 offres — que la routine avait avalé). Seuil à 3 manques : en dessous le bruit des singletons domine. La vue est en `security_invoker` — après avoir refermé les fonctions `SECURITY DEFINER` en ADR-37, ouvrir une vue qui contourne la RLS aurait été incohérent. La colonne `libelles_bruts` expose ce que chaque règle a regroupé : sans elle, impossible de vérifier qu'une règle ne fusionne pas deux choses différentes. (2) **Le bloc s'affiche dans Jobs Radar, pas dans un nouvel onglet ni dans le groupe Apprentissage.** Celui-ci est mort parce qu'il reposait sur un auto-diagnostic déclaratif (`skill_radar` figé au 2026-04-04, `strengths`/`gaps` NULL) et sur du contenu poussé que personne n'ouvrait ; ici la source est inversée — c'est le marché qui parle — et l'affichage est dans un onglet réellement fréquenté. Cliquer un axe filtre la liste et force le statut à « Tout », sinon le compteur du bloc ne correspondrait plus à la liste. (3) **La relance est un événement, pas une étape de funnel** : `last_followup_at` + `followup_count` (`sql/030`), et non un statut `relance_1` qui aurait été mutuellement exclusif avec `applied` et aurait appelé `relance_2`, `relance_3`… Les statuts `interview`, `rejected`, `ghosted` sont ajoutés — trois valeurs, pas un CRM. (4) **Le chargement passe à deux requêtes** : tout l'actif sans plafond utile, plus un échantillon de 300 archivées trié par score — filtrer simplement sur les statuts actifs aurait vidé les filtres « Clôturées » et « Tout », qui s'appuient sur `closed_at` des lignes archivées.

**Conséquences.** Le verdict de l'agrégat est net et converge avec le radar déclaratif de l'utilisateur : **Profondeur technique ML / MLOps manque sur 91 des 93 offres qui l'exigent (98 %)**, contre 50/116 pour le product management IA. Une dérive de règle est assumée et tracée : `ai/ml product` tombe dans « profondeur ML » plutôt que « product IA » parce que la règle ML s'évalue en premier — `libelles_bruts` permet de l'auditer. **`applied_at` reste NULL sur les 32 candidatures existantes** : il n'y avait rien d'honnête à backfiller, `updated_at` suivant les rescans de la routine (vérifié le 2026-08-17 — l'offre Accor porte `updated_at` au jour même pour une candidature antérieure). Le front dégrade donc le libellé en « vue il y a N j — date de candidature inconnue » plutôt que d'affirmer une date fausse ; le problème s'éteint de lui-même à mesure que la file se vide. Côté mobile, `cockpit/styles-mobile.css` ne contenait **aucun sélecteur `.jr-`** : le panel se repliait à 900 px puis plus rien, et `.jr-scan-grid` restait à deux colonnes de ~160 px sur un écran de 390 px. Un bloc dédié est ajouté, et le commentaire d'en-tête du fichier dit désormais **quels panels ont réellement été audités pour le mobile** — c'est ce silence qui avait rendu le trou invisible. Enfin, React passe des builds de développement aux builds de production (1,1 Mo → 138 Ko non compressés) : le gain n'est pas le réseau, que le cache CDN couvrait déjà, mais le parse/compile à chaque ouverture de page. Sonde de valeur du lot : `jobs_action` avec `action:"followup"`. Si ce compteur reste à zéro alors que 30 candidatures sont en souffrance, le bouton n'était pas le blocage et le problème est ailleurs.

## ADR-40 · 2026-08-19 · Tracker jeux — `game_releases.title` porte le nom du jeu, pas le libellé de l'événement

**Contexte.** Les deux producteurs de `game_releases` écrivaient le type d'événement *dans* le titre : `pipelines/igdb_map.py` pour les quatre types (`À venir : X`, `Date annoncée : X — 2026-09-04`, `Sorti : X`, `Annulé : X`) et `cockpit/lib/games-view.js::announcedRows()` pour `announced`. Or `event_type` et `event_date` sont déjà des colonnes. Le doublon ne s'était pas vu tant que la seule surface de lecture était le rail Gaming, parce que `buildUpcoming()` résout le nom réel via `title_id` dans `game_titles` et n'utilise `title` qu'en repli — le commentaire « le rail affiche des JEUX, pas des libellés d'événement » date de cette époque et contournait le problème au lieu de le corriger. L'encart Jeux du Brief, lui, lit `title` directement (Tier 1 léger, il ne charge pas `game_titles`) et affichait donc « À venir : Fire Emblem: Fortune's Weave » sous un tag « ANNONCÉ », et aurait affiché « Date annoncée : X — 2026-09-04 » à côté de sa propre colonne de date depuis la refonte du même jour. Le repli de `buildUpcoming()` portait en plus un défaut propre : `^[^:]+ : ` amputait n'importe quel nom légitime contenant un deux-points entouré d'espaces — « Persona 5 : Royal » devenait « Royal ».

**Décision.** `title` porte le nom du jeu, nu. Un fait, un endroit : le type vit dans `event_type`, la date dans `event_date`, et c'est à l'affichage de composer la phrase. Les deux producteurs sont corrigés dans le même commit — ils répliquent la même règle par construction (ADR-36) et le commentaire croisé des deux fichiers prévient qu'en toucher un seul les fait diverger en silence. Les 8 lignes existantes ont été reprises en base (toutes `announced`, toutes préfixées ; les deux-points internes de « Black Myth: Zhong Kui » ou « Hollow Knight: Silksong - Sea of Sorrow » sont intacts). Le repli est conservé mais resserré sur les quatre libellés connus (`stripEventLabel()`, exporté et réutilisé par l'encart du Brief) : il ne sert plus qu'à absorber une ligne écrite par un client dont le JS n'a pas encore été rechargé, et ne peut plus amputer un nom légitime.

**Conséquences.** Ceci supersède le passage d'ADR-36 qui verrouillait « le libellé exact `À venir :` » comme contrat d'idempotence entre les deux producteurs : la propriété visée — les deux producteurs écrivent le même texte pour la même ligne — est préservée et même renforcée, puisque ce texte est désormais une donnée d'IGDB et non une chaîne à recopier à l'identique de part et d'autre. Le contrat reste verrouillé par les mêmes tests des deux côtés (`tests/test_igdb_map.py`, `tests/test_games_view.mjs`), avec deux ajouts : un garde-fou qui vérifie qu'aucun des quatre libellés ne refuit dans `title`, et un cas qui prouve que le repli laisse « Persona 5 : Royal » entier. **Le même défaut existe à l'identique pour la Médiathèque** — `pipelines/media_tracker_common.py:64` écrit `Date annoncée : {label} — {date}` dans `media_releases.title`, et `MdtBriefCard` affiche `title` suivi de `event_date`, donc la date deux fois. Non corrigé ici : autre table, autre pipeline, hors du périmètre demandé.

## ADR-41 · 2026-08-20 · Une surface de lecture dédiée pour la santé du cockpit

**Contexte.** La santé était écrite trois fois et lisible nulle part : le bandeau du Brief ne montre que les pannes, la liste de Stacks & Limits est noyée dans un onglet qui parle d'argent, l'issue GitHub vit hors du cockpit et parle en `pipeline_id`. Aucune des trois ne dit ce qu'une panne coûte ni quoi faire. S'y ajoutaient trois angles morts mesurés le 2026-08-20 : `jobs_radar_routine` (sous `external_routines:`, une clé que le contrôle ne lisait pas — la panne d'ADR-31), `backup_supabase` (surveillé par lui-même seulement) et le contrôle lui-même ; plus quatre sondes de fraîcheur fausses ou absentes, dont `anime_tracker_sync` qui mesurait une table écrite aussi par `tmdb_tracker_sync`.

**Décision.** Un onglet Santé dans un groupe « Coulisses », alimenté par `pipeline_health` déjà chargée en Tier 1 — aucun fetch. Le contrat `health` de `pipelines.yaml` gagne quatre clés : `domain` (section, vocabulaire fermé de 7 valeurs, imposé par `validate-arch`), `filter` (sonde restreinte aux lignes qu'écrit ce pipeline), `remediation` (le geste qui répare) et `impact` (la phrase d'effet quand aucun onglet n'est concerné). La liste de Stacks & Limits est remplacée par un renvoi ; le bandeau du Brief est inchangé et gagne un lien.

**Pourquoi le geste vit dans le YAML.** Il ne peut pas se déduire à l'exécution : « recharger le crédit Anthropic » n'est nulle part dans un code HTTP 400. Le déclarer à côté du pipeline qu'il répare le fait vivre dans la même PR que lui, sous la même relecture. L'alternative — une table de correspondance en JS — l'aurait éloigné de ce qu'il décrit.

**Ce qui est assumé.** Un onglet de plus dans un cockpit qui en compte déjà des morts : la sonde est `section_opened{section:"sante"}`, et la règle est écrite d'avance — zéro ouverture en six semaines alors que le bandeau s'est affiché, on retire. `remediation` vieillira avec les services qu'il décrit, sans garde-fou automatique possible : une ligne sans geste reste utile.

## ADR-42 · 2026-08-20 · Médiathèque — les types de média deviennent des sections, pas un filtre

**Contexte.** ADR-29 a fait entrer les séries et les films dans la Médiathèque en les traduisant dans le vocabulaire AniList à l'ingestion. Tout le reste a suivi mécaniquement : fiche, progression par saison, notes, sorties, `tmdb_tracker_sync`. La surface, elle, s'est arrêtée à trois chips de type dans l'en-tête de « Ma collection », avec « Anime » seul coché par défaut pour ne pas noyer les 44 franchises existantes. Onze mois plus tard le compte est de 47 animes, 2 séries, 1 film : la fonctionnalité était complète et invisible. Un chip décoché par défaut, planqué sous un pli lui-même fermé par défaut, n'est pas une porte d'entrée.

**Décision.** Une barre d'onglets sous le titre, une section active à la fois, mémorisée. La section gouverne le hero, le rail, l'agenda et la collection. Une section = un `media_type`, déclaré dans `MDT_SECTIONS` — en ajouter une tient dans une ligne, ce qui était la demande. Le filtrage vit dans `mediatheque-view.js` (`typeOf` / `cardsOfSection` / `countBySection`), pas dans le panel, pour que le repli `media_type` null ⇒ anime soit testé : il décide à lui seul du sort des 47 franchises antérieures à TMDB.

**Ce qui refuse délibérément de suivre la section.** Le bandeau Sorties et la bande « Ce soir » sont rendus **au-dessus** des onglets. Leur portée est la bibliothèque entière et leur place doit le dire. Pour « Ce soir » c'est la décision du 2026-07-25 maintenue : la question du soir est « qu'est-ce que je regarde », pas « quel anime », et la restreindre à l'anime viderait le budget « 2 h+ » de son sens puisqu'un épisode dure 24 minutes. Corollaire assumé : entre 18 h et 2 h, aucun hero n'est rendu, dans aucune section — l'invariant « une seule surface de mise en avant » ne se répare pas en éloignant les deux de 200 px.

**Ce qui est assumé.** Cette PR ne crée aucune fonctionnalité : elle rend accessible ce qui existait. Si le volume de `mediatheque_section{section:"tv"}` reste nul, la conclusion ne sera pas « il faut plus d'UI » mais « la visibilité n'était pas le problème » — l'inverse de ce qu'on a supposé ici. La bande « Avant l'épisode » ne vit que dans la section Anime, ce qui n'est pas un choix éditorial mais une conséquence : `jp_vocab_sync` filtre `media_type == "anime"` et il n'existe aucun mot pour une franchise TMDB.

## ADR-43 · 2026-08-21 · Médiathèque — le manga entre sans calendrier, et une brique sans source se retire

**Contexte.** La section Manga a été demandée comme « la même logique que pour les séries ». Elle ne l'était pas. Le tracker parlait « épisode » de bout en bout — CHECK `kind` sans valeur pour un tome, colonnes `episodes_total` / `next_episode_number`, deux clients AniList codant `type: ANIME` en dur. Et surtout : l'utilisateur **achète ses mangas en VF**, il ne lit pas de scans. L'unité utile est donc le tome français et l'alerte utile serait « le tome 12 sort chez Ki-oon le 14 mars ».

Cette donnée n'a pas de source atteignable. Cinq sondées le 2026-08-21 : MangaDex n'agrège que de la scanlation anglaise ; OpenLibrary rend 0 résultat sur du manga francophone ; Nautiljon répond 403 derrière Cloudflare, refus explicite de robots qu'on ne contournera pas ; le quota anonyme de Google Books est épuisé (429 — non concluant, pas négatif) ; le dépôt légal BnF est par construction rétrospectif. AniList ne connaît que l'édition japonaise.

**Décision.** Le manga entre comme quatrième section (ADR-42), avec hero, rail, collection, statuts, notes et mise de côté — mais **sans agenda ni bandeau Sorties**. Une brique sans source ne se dégrade pas, elle se retire : deux rayons vides se lisent comme une panne, et l'utilisateur y revient plusieurs fois avant de comprendre qu'ils ne se rempliront jamais. Une entrée = une série (`kind='manga'`), `episodes_total` = tomes depuis `volumes`, jamais `chapters` — 224 chapitres à la place de 29 tomes serait illisible pour quelqu'un qui achète des volumes reliés. Un seul compteur, donc aucune migration hors le CHECK.

**Pourquoi `anime_tracker_sync` est étendu et non dupliqué.** Le réflexe, par symétrie avec `tmdb_tracker_sync`, était un pipeline séparé. Il est trompeur : `tmdb_tracker_sync` existe parce que TMDB est une *autre* API. Ici c'est la même, et deux sondes l'ont établi — les ids AniList ne collisionnent pas entre ANIME et MANGA (`Media(id:30642, type:ANIME)` → `Not Found`), et un `id_in` sans filtre de type ramène les deux dans un seul appel. Un pipeline séparé aurait payé un workflow, un cron et une sonde de santé pour dupliquer un batch identique.

**Le garde-fou anti-fausse-alerte, et où il vit.** Un prédicat pur `emits_events(franchise)` renvoie `False` pour un manga : aucun `media_releases` n'est jamais écrit pour lui. Un 30ᵉ tome paru à Tokyo n'est pas une sortie VF et peut précéder l'édition française de deux ans ; l'alerte serait fausse par construction et remonterait jusqu'au Brief du jour. Il ne vit **pas** dans `diff_events()`, qui est partagée avec `tmdb_tracker_sync` et dont le test défend explicitement l'agnosticisme : « quels types méritent une alerte » est une politique de pipeline, pas une règle de comparaison de lignes. Corollaire non négociable : `franchises_qs()` sélectionne `media_type`, sans quoi le prédicat lirait `None`, renverrait `True`, et les fausses alertes partiraient avec tous les tests au vert.

**Ce que l'implémentation a démenti.** La spec affirmait que l'agenda se retirerait tout seul, faute de dates. Faux : la branche de repli `RELEASING && in_main_chain` de `buildWeek` — ajoutée le 2026-07-25 pour qu'une saison à la date périmée ne s'évapore pas entre deux syncs — fabriquait une ligne « date inconnue » pour tout manga en cours de publication, c'est-à-dire dans son état normal. Le retrait est donc explicite. Deux autres pièges du même genre : `released()` rendait 0 pour un manga `RELEASING` et **désactivait le stepper**, rendant tout manga en cours non déclarable ; et `pruneDanglingEdges` (JS comme Python) ne gardait une arête que si sa cible était ANIME, élaguant donc chaque arête manga→manga et réduisant silencieusement toute franchise manga à son ancrage, le prune tournant avant `build_franchise`. Aucun des trois ne se voyait à la lecture.

**Ce qui est assumé.** Le dénominateur affiché est le nombre de tomes **japonais** : « 11 / 37 » signifie « 11 lus sur les 37 que compte la série », pas « 37 disponibles en français », l'édition VF accusant couramment un à trois ans de retard. Cela ne se corrige pas côté code. Aucune alerte de sortie, jamais — si une source VF fiable apparaît, elle se branchera sur les `media_releases` existants, c'est la donnée qui manque et non le schéma. Manhwas et manhuas partagent la section (AniList les type `MANGA` avec `countryOfOrigin` KR/CN) et aucune colonne « pays » n'est stockée. Enfin la sonde de survie : aucun `mediatheque_progress` sur une entrée `kind:'manga'` pendant six semaines alors que la section a été ouverte signifie que déclarer sa progression de lecture n'est pas un geste que l'utilisateur fait, et la section se retire.

## ADR-44 · 2026-08-21 · Veille — un garde-fou qui détruit la récolte n'est pas un garde-fou

**Contexte.** ADR-38 a posé, le 2026-08-17, un cliquet `MAX_DEAD_FEEDS = 16` : le run échoue dès qu'un flux de plus meurt, sans rougir chaque jour pour une dette déjà chiffrée. L'intention était juste — 16 sources sur 43 étaient muettes depuis des mois sans que rien ne le dise. L'exécution a coûté quatre jours de veille.

Trois défauts se sont additionnés. **Le socle a été mesuré en local et le pipeline tourne sur un runner** : plusieurs flux répondent 200 depuis une IP résidentielle et 403 depuis une IP datacenter — vérifié sur `importai.substack.com/feed`, même URL, même User-Agent, même jour. Le vrai socle valait 17 sur le runner. Le cliquet n'a donc jamais été vert en production : 0 run sur 4. **Le contrôle était placé avant toute persistance** : le `raise` tombait au step 2/9 alors que `save_to_supabase` est au step 7/9, si bien que le run du 2026-08-21 a collecté 53 articles valides et les a tous jetés, laissant cinq tables sans écriture — `articles`, `daily_briefs`, `wiki_concepts`, `signal_tracking`, `gemini_api_calls` — et douze onglets sur des données gelées. **Et le contrôle mesurait la mauvaise grandeur** : un run qui ne ramenait aucun article sortait vert, un run qui en ramenait 53 sortait rouge.

Hypothèse testée et écartée en passant : les codes 403 et le 418 (« I'm a teapot ») évoquaient un anti-bot déclenché par l'User-Agent par défaut de feedparser. Vérifié sur les 17 flux avec un UA navigateur — **aucun ne ressuscite**. Aucun header n'a donc été ajouté à `feedparser.parse()`.

**Décision.** Séparer la détection de l'avortement. `fetch_recent_articles()` rend `(articles, dead)` et **ne lève plus jamais** ; `main()` prend sa décision à la toute fin, après le step 9/9, après toutes les écritures Supabase et après l'email. Le run peut alors rougir sans rien détruire. Deux causes distinctes de code 1, cumulables et rapportées ensemble : la collecte passe sous `MIN_ARTICLES = 5` (les jours verts d'août ramenaient 25 à 56 articles — en dessous de 5 ce n'est plus une journée faible, c'est une panne de collecte), ou un flux muet ne figure pas dans le socle.

Le compteur entier devient un **ensemble nommé** `KNOWN_DEAD_FEEDS`, indexé par `section/nom`. Un entier ne distingue pas « 17 morts dont les 16 connus » de « 17 morts dont 3 nouveaux » et ne nomme pas le coupable ; un ensemble fait les deux, et le message d'échec cite le flux fautif avec sa raison. Le cas symétrique est traité : une clé du socle qui reparle produit un message invitant à la retirer — un cliquet qui ne redescend jamais finit par tout autoriser.

**Les 17 flux morts sont réparés, pas seulement chiffrés.** Douze changent d'URL, cinq changent de source quand le blog est éteint (The Batch vers AINews, Langfuse vers Arize, GreenTech Media vers Latitude Media, RTE vers Connaissance des Énergies, IEEE Smart Grid vers IEEE Spectrum Energy). Le corpus reste à 43 flux. Deux cas méritent d'être signalés : `Anthropic News` n'a **aucun** flux officiel de remplacement — quinze URL candidates testées, toutes en 404 — et passe par un miroir tiers non officiel de `claude.com/blog` hébergé sur GitHub Pages ; et `Import AI` migre de Substack vers le site WordPress personnel de son auteur, précisément pour échapper au blocage d'IP.

**Conséquences.** La procédure de calibration change et devient la règle : **le socle se remplit uniquement depuis les lignes `[DEAD]` du log d'un run réel sur le runner, jamais depuis une mesure locale.** `KNOWN_DEAD_FEEDS` est donc seedé **vide**, et le premier run peut légitimement sortir en code 1 en nommant les flux que l'IP du runner ne joint pas — ce n'est pas une régression, c'est la calibration prévue, et elle ne coûte plus aucune donnée. Le test qui gravait la valeur `16` en dur est remplacé : un test qui affirme « la constante vaut 16 » ne détecte rien, il empêche seulement de la corriger — celui-là aurait bloqué ce correctif. Les assertions portent désormais sur le comportement (socle exact vers vert ; socle plus un vers rouge en nommant le nouveau ; socle moins un vers vert avec invitation à nettoyer ; collecte sous le plancher vers rouge), et la collecte est vérifiée ne jamais lever, même avec 43 flux morts sur 43.

**Ce qui est assumé.** Les 17 URL ont été vérifiées depuis une IP résidentielle : c'est exactement le biais qui a produit le socle de 16, et c'est pourquoi le socle repart vide plutôt que d'être écrit d'avance. Le miroir Anthropic dépend d'un tiers qui peut s'arrêter sans préavis, et `feed_failure()` ne sait pas voir un flux gelé — il ne détecte que les 4xx et le zéro-entrée, jamais un flux qui répond 200 avec des items de 2024. Cette classe de panne reste non couverte.

## ADR-45 · 2026-08-21 · Santé — l'alerte notifie aux transitions, le déclenchement est surveillé, la table est élaguée

**Contexte.** ADR-38 a sorti l'alerte du cockpit en faisant ouvrir à `pipeline_health` une issue GitHub « Pipelines dégradés », réécrite à chaque contrôle quotidien et jamais commentée — pour ne pas produire environ 365 notifications par an. Le mécanisme a parfaitement fonctionné sur le fond : l'issue #9 était ouverte, exacte et à jour, elle nommait les six pipelines dégradés, leur cause et le lien du run. Elle avait aussi **zéro commentaire et n'avait notifié personne**. GitHub ne notifie que sur création et sur commentaire : réécrire un corps ne prévient pas. Le seul événement notifiant remonte au 2026-08-17, sur un état antérieur à la panne du 18. Quatre jours plus tard, la panne a été rediagnostiquée depuis zéro alors que la réponse était déjà écrite.

Trois angles morts sont apparus dans la même enquête. `verdict()` ne regarde **jamais l'âge du dernier run**, seulement sa conclusion et la fraîcheur d'une table : pour `backup_supabase`, qui n'écrit aucune table par conception (ADR-37), aucun signal n'existe — un cron qui cesserait d'être déclenché laisserait la brique verte indéfiniment, et c'est la seule dont la panne serait irrattrapable. `RUNS_TO_INSPECT = 15` applique la même fenêtre à un workflow bihoraire (30 heures d'observation) et à un hebdomadaire (15 semaines), d'où un `last_success_at` écrit à NULL sur `tft_sync` alors que le vrai dernier succès est le 2026-04-24. Et le catalogue est filtré sur `status: active` **à la lecture** seulement : une ligne déjà écrite n'est jamais effacée, donc un pipeline retiré du catalogue resterait affiché « en panne » pour toujours.

**Décision.** L'alerte **commente aux transitions de l'ensemble dégradé**, pas à chaque contrôle : un pipeline qui entre ou sort de l'ensemble déclenche un commentaire unique disant ce qui a changé, le cron restant quotidien. Appliquée au 18 août, cette règle aurait produit exactement une notification. Un troisième signal, `max_run_age_hours`, mesure le **déclenchement** là où `table` et `max_age_hours` mesurent la **sortie** ; il est déclaré à 192 h sur `backup_supabase` (168 h de période hebdomadaire plus 24 h de marge pour le retard de déclenchement GitHub, couramment de 30 à 60 min). Quand le compteur d'échecs sature sa fenêtre, la vraie date du dernier succès est obtenue par un appel ciblé plutôt qu'écrite à NULL. Et la table est **élaguée** : toute ligne dont le `pipeline_id` a quitté le catalogue actif est supprimée, avec un garde-fou explicite contre le catalogue vide ou illisible.

`tft_sync` passe en `status: paused` — statut ajouté au vocabulaire du catalogue — et son cron est retiré. Sur 1 170 runs depuis le 2026-04-20, 9 sont verts et **les 9 tiennent dans une fenêtre de 22 h 35**, soit exactement la durée de vie d'une clé Riot de développement. Ce workflow pesait environ 88 % de tout l'historique rouge du dépôt et noyait les vraies pannes. Une rotation de secret n'est pas un correctif : il faut une Personal API Key non expirante, obtenue hors du dépôt.

Enfin, le périmètre de la sauvegarde s'élargit de 22 à 26 tables. Le critère annoncé — « ce qu'aucun pipeline ne sait refabriquer » — avait été appliqué en regardant *qui produit* la donnée, sans se demander si le producteur en est encore capable. Il devient « refabricable **à l'identique** », ce qui inclut tout ce qui est daté : `usage_events` (seule mesure de l'usage réel du cockpit), `daily_briefs`, `signal_tracking`, `jarvis_conversations`.

**Conséquences.** Le champ `panels` du contrat health de `daily_digest` est corrigé de 3 à 12 onglets, par intersection de `output_tables` avec les `reads` de `dependencies.yaml` : il était rempli en pensant à la table principale, et c'est pourquoi neuf onglets ont affiché des données gelées pendant quatre jours sans le moindre avertissement. Le seuil `max_run_age_hours` ne transite **pas** en base : la colonne n'existe pas et l'ajouter à la ligne upsertée ferait échouer tout l'upsert en PGRST204. Il ne sert qu'au verdict et à la phrase de cause ; l'afficher à côté de l'âge du run demanderait une migration, non faite ici.

**Ce qui est assumé.** Rien de tout ceci ne répare une panne : quatre des six pipelines dégradés le sont à cause d'une identité expirée hors du dépôt — crédit Anthropic, application Strava désactivée, token Withings mort, clé Riot de développement — et aucune ligne de code n'y peut quoi que ce soit. Le dépôt a beaucoup investi dans l'observabilité et cet investissement fonctionne ; c'est la boucle de remédiation qui manquait. Test de non-régression de cette décision : si dans un mois l'issue #9 liste encore `strava_sync`, `withings_sync` et `tft_sync`, le problème n'aura jamais été technique.

## ADR-46 · 2026-08-21 · Portage mobile du cockpit — une adaptation de `index.html`, pas une seconde entrée

**Contexte.** ADR-30 avait tranché en faveur d'une seconde page d'entrée pour la Médiathèque, sur un ratio mesuré : 859 ko de JSX transpilés par Babel standalone pour `index.html` contre 71 ko pour `mediatheque.html`, soit 12 pour 1 sur le coût dominant du démarrage à froid sur iPhone. Le portage du cockpit complet à ses 31 onglets pose la même question : seconde entrée dédiée, ou adaptation de `index.html` lui-même ?

**Décision.** `index.html` est adapté sur place. Le ratio de 12:1 ne s'applique pas ici : il venait entièrement de l'exclusion des 29 autres panels par la page dédiée à la Médiathèque — ce qu'un portage du cockpit *complet* ne peut par définition pas faire, puisque son périmètre est l'ensemble des onglets. Une page dédiée au cockpit entier transpilerait le même volume que `index.html`, sans le rapport qui justifiait le choix inverse pour la Médiathèque. Second facteur : le test sur appareil du 2026-08-21 (Safari iPhone, cockpit complet) n'a fait ressortir aucune lenteur au démarrage — l'hypothèse qui aurait pu compenser l'absence de gain ne s'est pas matérialisée.

**Conséquences.** Une seule entrée pour le cockpit mobile, pas de divergence nouvelle à maintenir entre deux coquilles HTML. `mediatheque.html` **est conservée** par décision explicite : son démarrage à froid douze fois plus rapide garde une valeur propre pour l'usage canapé (ADR-30), et la retirer maintenant supprimerait une surface avant de savoir si le cockpit mobile prend. Toute globale nouvellement lue par un panel commun aux deux entrées doit continuer d'être déclarée dans les deux HTML — invariant déjà verrouillé par `tests/test_mediatheque_entry.mjs`, étendu par ce lot à `tests/test_mobile_entry.mjs` pour `cockpit/lib/mobile-view.js`, `cockpit/lib/telemetry.js`, `cockpit/components-mobile.jsx` et leur ordre de chargement.

## ADR-47 · 2026-08-21 · Une sonde incapable de distinguer « inutilisé » de « cassé » n'est pas une sonde

**Contexte.** `usage_events` n'accepte les `INSERT` que du rôle `authenticated` (`usage_events · INSERT · roles={authenticated} · with_check=true`). Un démarrage qui meurt avant l'authentification n'écrit donc aucune trace. ADR-30 avait confié à une sonde `surface: "pwa"`, portée par les events `mediatheque_*` et `jp_*`, la décision de savoir si le portage PWA de la Médiathèque avait trouvé son usage — avec un délai de trois semaines. Cette sonde ne pouvait structurellement pas répondre à sa propre question : « surface non utilisée » et « surface cassée » produisent exactement le même silence dans `usage_events`. Les trois semaines de mesure n'ont rien tranché, ni dans un sens ni dans l'autre — un flou repéré seulement en cherchant, longtemps après l'échéance, pourquoi la PWA Médiathèque semblait morte.

**Décision.** Toute décision confiée à une mesure exige d'abord de vérifier que la mesure peut voir l'échec qu'elle est censée détecter. Quand elle ne le peut pas — comme ici, où l'événement qui prouverait la panne est justement celui que la panne empêche d'écrire —, le diagnostic doit s'afficher là où l'utilisateur se trouve, pas dans une table qu'il ne consultera jamais. D'où le délai de garde du loader (`cockpit/lib/bootstrap.js`) : passé 8 secondes sans authentification résolue, « Chargement du cockpit… » est remplacé par l'étape qui a bloqué (scripts manquants, `waitForAuth` non résolu, Tier 1 en erreur, panel jamais enregistré) — lu sur l'appareil, à un endroit où aucun Web Inspector n'est joignable depuis Windows.

**Conséquences.** Le champ `viewport` posé sur `track()` dans ce même lot (voir `docs/telemetry.md`) hérite du même angle mort que la sonde d'ADR-30 : il ne verra jamais un démarrage avorté, seulement ce qui est allé assez loin pour appeler `track()`. C'est pourquoi le délai de garde du loader compte davantage que lui pour diagnostiquer une panne, même s'il reste la bonne mesure continue pour arbitrer les vagues 3 à 5. À rapprocher d'ADR-45, où l'alerte de santé pipeline était enfermée dans les onglets même que la panne avait fait déserter (`strava_sync` / `withings_sync` alertaient sur `perf`, zéro ouverture en 30 jours). Même famille de défaut — une sonde ou une alerte placée là où l'échec qu'elle doit détecter l'empêche justement d'être vue —, troisième occurrence après ADR-30 et ADR-45.

## ADR-48 · 2026-08-25 · Strava — un accès retiré se met en pause déclarée, il ne se répare pas

**Contexte.** `strava_sync` échouait tous les jours depuis le 2026-07-01, 15 runs rouges d'affilée au 25 août. Le diagnostic posé le 15 août — application Strava `Inactive` — était juste mais incomplet : il laissait croire à un geste administratif oublié. La cause réelle est que **les appels à l'API Strava sont devenus réservés aux abonnés payants**. L'accès n'a pas été perdu, il a été retiré.

Trois faits mesurés le 25 août cadrent la décision. D'abord, `refresh_access_token()` renvoie toujours **HTTP 200** avec `token_rotated=False` : Strava émet encore des access_tokens, le grant OAuth est intact, seuls les `/api/v3/*` répondent 403 `resource: Application / field: Status / code: Inactive`. Ce n'est donc ni un scope, ni une révocation, ni un quota — et **rejouer `scripts/strava_oauth_init.py` ne répare rien**, contrairement à ce qu'affirmait le champ `remediation` du catalogue, qui prescrivait ce geste en renvoyant vers `docs/strava-setup.md`. Une remédiation qui prescrit un geste inopérant coûte plus qu'une remédiation absente : elle fait conclure à un échec du geste plutôt qu'à une erreur de diagnostic. Ensuite, le reste de la chaîne est sain : la persistance du token tourné (`user_profile.key` est la PK, l'upsert `merge-duplicates` vise la bonne cible, la fonction lève au lieu de warner), le câblage front, le lookback de 365 jours qui rattraperait les huit semaines manquantes en un seul run. Enfin, `strava_activities` s'arrête au 2026-06-30, 75 lignes.

**Décision.** `strava_sync` passe en `status: paused`, son cron est retiré, le `workflow_dispatch` reste. C'est la reconduction exacte du traitement de `tft_sync` (ADR-45) : quand la cause vit hors du dépôt et qu'aucun code ne la rend, un cron quotidien ne produit que du rouge qui noie les vraies pannes. La ligne `pipeline_health` est élaguée au contrôle suivant, comme prévu. Le flow `perso-strava.yaml` reste `active` : il décrit une architecture intacte, pas un état d'exécution — `archived` est réservé aux suppressions (cf. `README.md`).

**Le panneau devait le dire, et il ne le pouvait plus.** L'élagage referme le seul canal qui signalait la panne sur l'onglet `perf`, pendant que ses chiffres, eux, restent affichés. Or `transformForme()` calcule les fenêtres glissantes contre la date du jour : une collecte arrêtée remplit « 7 derniers jours », « 30 derniers jours » et le streak de zéros, et le hero titrait « **0 séance cette semaine** » en plus gros caractère de la page. Ces zéros sont **indiscernables d'une vraie inactivité** — et le catalogue interdit de trancher automatiquement, puisque la fraîcheur de `strava_activities` y est mesurée mais jamais sanctionnée, précisément parce que ne rien écrire est nominal pour un pipeline piloté par l'usage. Le panneau ne peut donc pas déduire son propre aveuglement : il faut le lui **déclarer**. D'où `FORME_SOURCES_EN_PAUSE`, une constante datée dans `data-loader.js`, exposée en `_sources_paused`, rendue par un bandeau qui réutilise les classes `.phb` du bandeau de santé (aucun CSS neuf) avec un point neutre et non le rouge d'alerte — une pause décidée n'est pas une panne. Le titre du hero, lui, cesse d'annoncer un chiffre faux et affiche la date de la dernière activité connue, calculée depuis la donnée et non codée en dur : si la source repart, il redevient juste tout seul.

**Réversibilité.** Reprendre tient en un commit : retirer l'entrée de `FORME_SOURCES_EN_PAUSE`, restaurer `schedule: '30 4 * * *'`, repasser `status: active`. Les trois secrets GitHub restent valides, aucune donnée n'a bougé, et le premier run rattrape tout l'historique. La séquence de validation est celle d'ADR-45 : abonnement, réactivation de l'app sur strava.com/settings/api, `workflow_dispatch`, vérifier le vert — et seulement alors le cron.

**Ce qui est assumé.** Les sections en aval du hero continuent d'afficher leurs zéros ; le bandeau les cadre, il ne les réécrit pas. Reprendre chaque état vide des sous-onglets Course et Workout demanderait de retoucher un panneau de 788 lignes pour un gain marginal une fois la cause annoncée en tête. **Withings n'est pas traité ici** : mort depuis le 2026-04-23 (3 mesures, token invalide), il n'est pas déclaré en pause parce qu'il n'est pas en pause — son cron tourne, `pipeline_health` le signale encore, et sa cause est réparable dans le dépôt (ADR-45 en donne la séquence). Le mécanisme `_sources_paused` est une liste, prête à l'accueillir si cette décision est prise. Enfin le catalogue affirmait un input `workflow_dispatch` « days » qui n'a jamais existé dans le workflow ; c'est corrigé au passage. Test de non-régression : si l'onglet `perf` est ouvert dans les semaines qui viennent et qu'il faut encore se demander « pourquoi zéro ? », le bandeau aura raté sa cible.

## ADR-49 · 2026-08-25 · Withings — la doc d'un contrat externe fait partie du mécanisme, pas du décor

**Contexte.** `withings_sync` échoue tous les jours depuis le 2026-04-24. La cause a été trouvée le 2026-07-26 : le pipeline jetait le refresh_token tourné, en s'appuyant sur une « période de grâce » Withings qui n'existe pas. Le code a été corrigé ce jour-là. Un mois plus tard, le pipeline est toujours mort — et `user_profile` ne contient toujours **aucune** clé `withings_refresh_token`, vérifié le 2026-08-25.

Deux raisons, et la seconde est la vraie décision de cette ADR. La première est connue : le correctif ne s'arme qu'**après** un refresh réussi, or le seul token disponible est mort depuis le 23 avril — il exige donc un OAuth manuel, hors du dépôt. La seconde ne l'était pas : **`docs/withings-setup.md` affirmait encore la croyance fausse**, mot pour mot — « the new token is NOT automatically written back […] Withings keeps the previous token valid for a grace period (usually days) ». Le code avait été corrigé, la phrase qui l'avait fait écrire de travers était restée. Elle décrivait le contrat externe à l'envers *et* décrivait le pipeline à l'envers, puisqu'il persiste désormais en base.

**Décision.** La description d'un contrat externe (rotation de token, quota, expiration) est traitée comme du mécanisme : quand le code qui l'implémente change, elle change dans le même commit. `docs/withings-setup.md` est réécrit — rotation à chaque appel sans grâce, secret GitHub à usage unique, source de vérité en base, persistance *avant* la récupération des mesures, et le symptôme exact d'un token mort (`status=503`, et non le 401 qu'annonçait la page). L'ancienne phrase est citée sur place avec ce qu'elle a coûté, plutôt que supprimée : c'est ce qui empêche de la réintroduire de bonne foi.

**Le coup est unique, donc il se vérifie avant.** Un OAuth manuel n'offre exactement qu'un essai — Withings invalide l'ancien token dès le premier appel. Les cinq points où cet essai pouvait être gaspillé ont été audités le 2026-08-25 et sont tous sains : la persistance a lieu **avant** `fetch_measurements` (un échec de récupération n'emporte plus le token), `save_refresh_token_to_supabase()` **lève** au lieu d'avertir, elle n'est **pas** court-circuitée par `--dry-run` (le token a réellement tourné, il doit être écrit quoi qu'il arrive), `user_profile.key` est la clé primaire donc l'upsert PostgREST `merge-duplicates` vise la bonne cible, et le test de permission de `withings_oauth_init.py` utilise l'**access_token** — il ne brûle donc pas le refresh_token qu'il vient d'afficher.

**Le premier run doit être un backfill.** `INCREMENTAL_DAYS = 7` : un run nominal ne demande à Withings que les sept derniers jours. Après quatre mois d'interruption, attendre le cron sauterait définitivement le 2026-04-24 → 2026-08-18, alors que Withings conserve l'historique côté serveur. Ce n'était écrit nulle part dans le chemin que suit quelqu'un qui répare — le script d'OAuth s'arrêtait à « copy into GitHub Secrets ». Il imprime désormais la séquence complète, `gh workflow run withings-sync.yml -f backfill=true` compris, et dit pourquoi ne pas la sauter.

**Conséquences.** `WITHINGS_USER_ID` cesse d'être présenté comme un secret à créer : la valeur n'est lue par aucun pipeline ni aucun workflow (vérifié par grep sur tout le dépôt), `user_id` étant rendu par le refresh lui-même. Une instruction qui fabrique un secret inutile n'est pas neutre — elle ajoute une étape à un mode d'emploi qu'on suit précisément dans les moments où l'on n'a pas le temps de le questionner.

**Ce qui est assumé.** Rien ici ne répare le pipeline : il faut un OAuth manuel, et lui seul. Cette ADR réduit la probabilité que cet essai unique soit gaspillé et que la panne se rejoue une troisième fois. Test de non-régression : si `user_profile.withings_refresh_token` existe et que `withings_measurements` dépasse trois lignes, la boucle s'auto-entretient — c'est le seul verdict qui compte. Écho non traité : `strava_sync.py` consomme le token en `--dry-run` sans le persister (`if not dry_run` autour de la sauvegarde), soit exactement le défaut corrigé ici. Dormant — Strava ne fait pas tourner son token et le pipeline est en pause (ADR-48) — mais c'est la même famille.

## ADR-50 · 2026-08-27 · Jobs Radar — le pilotage cesse d'être une exception tolérée, la boîte tech devient un critère

**Contexte.** Jean observe que le radar ne lui montre presque que des PM IA, qui exigent 7 à 10 ans d'expérience produit là où il en a 3. Son expérience réelle, c'est le pilotage de projet et de programme — 8 ans sur 11. La mesure sur 60 jours confirme et précise : `produit` 246 offres pour 77 `new` (moyenne 4,0), mais `pgm` 91 → 12 (2,9), `em` 63 → 3 (2,6), `cos` 33 → 5 (3,2) et `pjm` 30 → **0** (2,4). Le pilotage n'était donc pas absent du radar : il était **collecté puis systématiquement enterré**.

Deux causes distinctes, qu'il fallait ne pas confondre. La première est un **problème de sourcing** : le top 40 des employeurs alimentant `pgm`/`pjm`/`em` était Safran, Wavestone, Capgemini, Accenture, MBDA, Square Management, Adone Conseil, Saegus, Oliver Wyman, Theodo — zéro licorne, zéro GAFAM. Les requêtes de pilotage portaient le suffixe `in France`, qui ramène des employeurs nationaux et industriels : `senior program manager in France` a produit **0 offre retenue sur 10**, quand sa variante `senior program manager Paris` ramène Criteo, Databricks et Parloa. La seconde est un **problème de rubric** : `job_pref_rules` posait « PM / RTE senior UNIQUEMENT si la boîte est tech/IA crédible » et l'ÉTAPE 3 exigeait l'IA au cœur du rôle sur `score_sector`. Un Program Manager chez Datadog scorait donc comme un PjM chez Capgemini.

Deux angles morts sont apparus dans la même enquête. `company_stage` range **Google et Safran dans le même bucket `grand_groupe`** : la notion de « boîte tech désirable » n'existait nulle part dans le modèle. Et `user_profile` ne portait **aucune donnée d'expérience** — ni années totales, ni répartition — si bien que `score_seniority` était deviné : un PjM chez Safran et un Senior PM chez Mistral atterrissaient tous deux à ~1,7/3.

**Décision — deux rangs de rôles cibles.** Le pilotage (Program Manager, Technical Program Manager, RTE, Delivery/Engagement Manager, Chief of Staff, PjM senior) en boîte tech désirable devient une cible de **premier rang**, au même titre que le cap produit IA. Les axes ne le pénalisent plus pour absence d'IA. Ce n'est pas un renoncement au pivot : c'est un **plafond à 6.9** qui porte désormais cette contrainte, et lui seul. Le seuil hot lead étant 7, un pilotage sans angle IA est visible et ne devient jamais hot lead — la règle est vérifiable d'un coup d'œil, là où « pénalise un peu » ne l'était pas.

**Décision — « boîte tech désirable » devient une définition écrite.** Un anti-critère disqualifie à lui seul : le business model est la vente de prestation intellectuelle (ESN, conseil, cabinet, staffing). Sinon il faut 2 critères sur 4 — produit tech propriétaire, trajectoire financée récente, densité d'ingénierie, marque tech reconnue — complétés par une liste d'ancrage nominative d'une cinquantaine de noms. La liste ancre les cas évidents ; ce sont les critères qui tranchent, précisément parce que Jean se sait biaisé quand il nomme des entreprises. Le tout vit dans `job_pref_rules` et **pas** dans `job_pref_observed` : l'ÉTAPE 7 réécrit la seconde tous les lundis et aurait effacé la règle. Le bonus associé est de **+1.5**, non cumulable avec le `+1.0 scale-up très tech` déjà présent dans `job_pref_observed` — on retient le plus élevé, jamais la somme.

**Décision — `score_seniority` cesse de deviner.** `job_pref_rules` porte désormais **deux compteurs** : 11 ans d'expérience, dont 8 de pilotage et 3 de produit. Une JD qui exige « 8+ years of product management » trouve 3 ans et non 11 (`score_seniority ≤ 1`) ; une JD qui exige « 8+ years of program management » trouve 8 ans (`≥ 2.5`). `rubric_justif.seniority` doit **porter les deux nombres** (`JD: 8 ans produit — profil: 3 ans`). C'est le même garde-fou que le calibrage chiffré d'ADR-33 : une justification sans nombre signifie que le test n'a pas été fait. Les offres de PM IA ne sont pas dégradées pour autant — elles restent visibles, l'écart est simplement nommé au lieu d'être subi.

**Décision — la pénalité TPM se lit sur la substance, jamais sur le titre.** `technical program manager Paris` s'est révélée la requête la plus riche en boîtes désirables de toutes celles testées (Databricks, Mistral AI ×2, Pigment, Parloa). La pénaliser au titre revenait à financer un gisement pour l'enterrer. Le -2.5 ne s'applique donc plus que si la JD attend une profondeur d'ingénieur (diplôme CS, system design, écriture de code, architecture) ; un TPM de pilotage en organisation technique n'en prend aucune. Le signal de Jean n'est pas nié — il est relu au bon endroit, et `job_pref_observed` portait déjà la mention « exception consignée » de sa candidature au TPM Engineering de Mistral en août 2026. L'ÉTAPE 7 reçoit l'instruction de conserver cette formulation : une ligne « titre TPM -2.5 » serait une régression.

**Décision — sourcing à 10 requêtes/run.** 6 de socle + 4 de rotation, soit **18 requêtes distinctes** contre 14, pour ~130 req/mois (65 % du quota) contre ~104. Le socle tient les deux cibles à la fois : 4 requêtes produit IA et 2 pilotage-tech (`program manager Paris`, `technical program manager Paris`). **Les 8 nouvelles formulations ont été testées contre JSearch avant d'être écrites**, sur le critère de la part d'employeurs tech et non du volume. Trois hypothèses ont été falsifiées par ce test et sont consignées dans le prompt : les tokens `SaaS` et `startup` attirent du commercial et des cabinets de recrutement (`program manager SaaS Paris` ramène des Key Account Manager) ; `chief of staff tech Paris` ne rend que ~3 offres mais avec une précision maximale (Malt, « Chief of Staff to the CTO »), son faible volume est normal et ne doit pas être diagnostiqué comme une panne ; et surtout **l'Engagement Manager n'est pas re-ciblable** — aucune variante ne le sort du conseil et de la vente en France, `engagement manager Paris` est donc conservée telle quelle puisque c'est par elle qu'était venue l'offre Postman.

**Ce qui est assumé.** **Aucun re-scoring rétroactif.** La routine ne re-score jamais une offre connue, et `jobs` ne stocke pas la description de l'annonce — seuls `title`, `company` et un `pitch` de deux phrases survivent, ce qui rend un re-scoring du stock matériellement impossible. Les 857 offres de pilotage archivées et jamais jugées gardent leur ancien score et s'éteindront par vieillissement. Le nouveau régime ne vaut que pour les scans à venir, à partir du 2026-08-28. Deuxième point assumé : ouvrir le pilotage en boîte tech fait mécaniquement entrer des TPM, et c'est le pari de cette ADR que la relecture par la substance les trie mieux que le titre ne le faisait. Correction de fait au passage : la date de reset du quota JSearch **n'est pas « le 27 de chaque mois »** comme l'affirmait `docs/cowork-routines/jobs-radar.md` — mesuré le 2026-08-27, l'en-tête `X-RateLimit-Requests-Reset` annonçait la fin de fenêtre à 22:22 UTC avec 60 requêtes restantes et non 200 ; seul cet en-tête fait foi. Test de non-régression : si dans un mois `pjm` et `pgm` affichent toujours 0 `new` en boîte tech désirable, ou si `rubric_justif.seniority` ne porte pas les deux nombres, le changement a échoué.

**Premier run, le jour même — le sourcing tient, la rubric a dû être durcie.** Run de test à 16h23 UTC : 10/10 requêtes en HTTP 200, `raw_count` 95 contre 62 et 76 aux deux runs précédents, 13 offres scorées. Les employeurs confirment la thèse : Parloa, Databricks, Mistral AI, Pigment, Datadog, Ornikar, Iliad-Free, Rexel, Alstom — là où le régime précédent produisait du Safran et du Capgemini. Les VETO ESN/conseil ont correctement archivé Valtech et ORPHOZ à 2.0. **Mais les quatre règles de scoring écrites le matin même ont toutes été violées** : aucune des 13 lignes ne porte le format imposé de `rubric_justif.seniority` (le modèle a écrit `3/3 Senior Field TPM` au lieu de `JD: n ans — profil: n ans`) ; 9 offres sur 13 ont reçu `score_seniority = 3.0`, signe qu'il notait la séniorité du poste et non le fit ; le bonus a été écrit `+1` au lieu de `+1.5` ; et le plafond n'a jamais mordu — un `Global IT/Digital Program Manager` chez Rexel, rang A sans angle IA, est sorti à **7.0 pile**, donc en hot lead, à un dixième du plafond. S'y ajoute une régression : `intel.source_query` est **NULL sur les 13 lignes**, ce qui casse le contrat d'ADR-31 et rend le rendement par requête immesurable — l'instrument même qui avait servi à diagnostiquer tout le reste.

**Leçon retenue, et corrigée le soir même.** Une règle descriptive (« nomme l'écart », « plafonne à 6.9 ») se dilue dans un prompt de 26 000 caractères ; une procédure mécanique ne se dilue pas. La v2 du prompt remplace la prose par : un **ordre de calcul numéroté en 5 étapes** où le plafond est un `min()` et non un jugement ; des **tokens littéraux obligatoires** dans `calibrage` (`boite tech desirable +1.5`, `plafond pilotage sans IA 6.9`) qui rendent le respect de la règle vérifiable par un `LIKE` en SQL ; un **format imposé** commençant par `JD: ` pour la clé `seniority`, avec les erreurs réelles de ce run citées comme contre-exemples ; et un bloc **CONTRÔLE AVANT ÉCRITURE** de 4 points à vérifier par offre avant l'INSERT. Deuxième leçon, méthodologique : **on ne peut pas re-tester une modification de rubric le même jour**. La dédup reconnaît les offres qui viennent d'être insérées et la routine ne re-score jamais une offre connue — un second run n'aurait eu presque aucune offre neuve à scorer. La vérification d'un changement de scoring attend donc nécessairement le run suivant.

## ADR-51 · 2026-08-31 · Panorama IA — une table à part plutôt qu'un élargissement du catalogue écosystème

**Contexte.** La demande était de faire refléter par la veille un type de contenu qu'elle ne produit pas : des outils IA rangés par cas d'usage, avec le modèle économique en clair (gratuit / freemium / payant), MCP compris, et une distinction entre ce qui touche directement le projet et ce qu'il faut simplement savoir situer. L'onglet `veille-outils` existait déjà avec deux sous-onglets, mais aucun des deux ne pouvait porter ça. `claude_veille` est un flux hebdomadaire éphémère, périmé d'une semaine sur l'autre : on n'y reparcourt rien. `claude_ecosystem` est un catalogue pérenne, mais **Claude-centré par construction** — son prompt dit « outils qui se pluggent à Claude ou auquel Claude se plugge » — et ses 17 colonnes n'ont **aucune notion de prix**. Ses deux axes de rangement, `direction` (inbound/outbound) et `type` (mcp_server, sdk, framework…), sont techniques.

**Décision — une table `ai_landscape` séparée (migration `sql/034_ai_landscape.sql`).** Élargir `claude_ecosystem` était l'option la plus économique en apparence et la pire en pratique, pour deux raisons distinctes. La première est **sémantique** : `direction: inbound` n'a aucun sens pour Midjourney, Veo ou Granola. On aurait obtenu une colonne obligatoire remplie au hasard sur la moitié des lignes, c'est-à-dire un filtre qui ment. La seconde est **arithmétique** : les ~535 lignes déjà présentes n'ont pas de prix, et personne ne backfille 535 tarifs à la main. Le filtre « gratuit » aurait affiché un sous-ensemble arbitraire — celui des lignes vues après la migration — sans que rien ne signale l'angle mort. C'est exactement le motif déjà rencontré sur Jobs Radar : un changement de schéma laisse le stock existant au vieux schéma, et le stock non re-scorable devient un mensonge silencieux.

Les deux tables coexistent donc avec des périmètres explicites : `claude_ecosystem` répond à « qu'est-ce qui se branche à Claude », `ai_landscape` à « qu'est-ce qui existe sur le marché, pour quel usage, à quel prix ». Le seul recouvrement assumé est le bloc `use_case = 'claude_stack'` (Cowork, Skills, Claude in Chrome, Claude for Excel), où le prix — inclus dans quel plan — est précisément l'information que l'autre table ne porte pas.

**Décision — deux axes neufs, et un jugement assumé.** `pricing_tier` en trois valeurs fermées, doublé d'un `pricing_note` libre qui porte le détail lisible (« 20 $/mois », « 3 images/jour offertes », « 0,75 $/s »). Et `relevance` en deux valeurs, `core` / `context`, qui encode la pertinence pour ce projet précis. Ce second axe est **un jugement, pas un fait** : il est juste au moment où il est écrit et devient faux si le projet change de direction, sans que rien ne le signale. Il est conservé malgré ça parce qu'un panorama de 99 entrées sans hiérarchie de pertinence est un annuaire, pas une veille. Le champ `applicability` porte la même charge au niveau de la ligne — 32 entrées sur 99 en ont une, et il vaut mieux qu'il reste vide que rempli par politesse.

**Décision — une passe de plus sur la routine existante, pas une troisième routine.** La routine Cowork mensuelle « Catalogue écosystème Claude » gagne une **passe 2** (prompt v2, `docs/cowork-routines/catalogue-ecosystem.md`) au lieu qu'on crée un job dédié. Le raisonnement est celui de la mortalité observée : le pipeline hebdomadaire et Jarvis Cloud sont éteints depuis des semaines pour la même raison — un compte Anthropic sans crédit — et la Médiathèque a montré qu'une surface peut paraître vivante sur un catalogage d'une seule semaine. Ajouter un troisième job, c'est ajouter une troisième chose qui peut mourir sans prévenir. Le coût est un run plus long (20-30 min contre 8-15) et un couplage : si la passe 1 échoue tôt, la passe 2 ne tourne pas.

**Décision — le prix est le seul champ dont le rafraîchissement est contractuel.** Le prompt impose de re-vérifier `pricing_tier` et `pricing_note` **pour tous les slugs existants à chaque run**, pas seulement pour les nouveaux, et de lister les changements de prix détectés dans le rapport markdown. Un free tier raboté est l'information la plus actionnable de cette table et la seule qui se périme vite. Le reste (description, use_case) bouge peu.

**Ce qui est assumé.** Le seed initial de 99 entrées vient d'une recherche web du 2026-08-31, pas des pages éditeur : les tarifs sont des ordres de grandeur issus de comparatifs tiers, et la table ne doit jamais servir de référence contractuelle. `use_case` est une contrainte CHECK à 17 valeurs — en ajouter une coûte une micro-migration, ce qui est délibéré : une taxonomie ouverte aurait dérivé au premier run de routine, comme la catégorie `em` de Jobs Radar avait dérivé faute de définition écrite. L'ajout manuel d'une entrée n'est **pas** implémenté en v1, contrairement au catalogue voisin qui a sa modale : le seed couvre le besoin initial, et une modale de plus ne se justifiera que si le manque se fait sentir. Enfin, un défaut préexistant reste ouvert et n'a pas été corrigé ici pour ne pas élargir le périmètre : `T2.claude_ecosystem()` fetch avec `limit=500` alors que le catalogue a dépassé 535 entrées — le sous-onglet Catalogue en tronque donc silencieusement une partie. `ai_landscape` est monté à `limit=1000` pour ne pas reproduire le défaut.

## ADR-52 · 2026-09-24 · Jobs Radar — lire une annonce n'est pas postuler, et trier tient en un geste

**Contexte.** L'utilisateur trouve que le fit des offres ne progresse pas. Mesuré le 2026-09-24, il a raison : la part des hot leads (≥ 7, doublons fusionnés) qu'il ouvre est plate depuis cinq mois — 37 % en avril-mai, 23 % en juin-juillet, 34 % en août, 33 % en septembre — malgré ADR-21, ADR-33 et ADR-50. Deux causes relèvent du front. **L'écran cache la nouveauté** : avec les filtres par défaut, le bloc hot leads comptait 82 cartes, dont 49 offres déjà « postulées », et une seule offre de la semaine parmi les 12 premières. **Le signal ment** : « Postuler sur LinkedIn » était le seul moyen d'ouvrir l'annonce — `jobs` ne stocke pas sa description — et il écrivait `status = applied`. `applied` voulait donc dire « ouvert » ; cinq offres étaient à la fois `applied` et 👎. L'ÉTAPE 7 de la routine lit pourtant `applied` comme « POSITIFS CONFIRMÉS PAR LES CANDIDATURES ». Le vote 👍/👎 n'a servi que 23 fois en cinq mois, et le recalibrage, qui exige 3 votes neufs, n'a pas tourné depuis le 2026-08-10.

**Décision — lire et postuler deviennent deux gestes.** « Lire l'annonce » ouvre le lien et n'écrit rien en base (`jobs_action {action:"open"}` seulement) ; « J'ai postulé » écrit `status = applied` + `applied_at`. À partir de la mise en production, `applied` signifie « candidature envoyée ».

**Décision — trier tient en un geste, et chaque geste est un signal.** « Pas pour moi » remplace le 👍/👎 et l'entrée « Archiver » : trois raisons à un clic (`pas crédible`, `trop junior`, `boîte ou secteur`) plus une précision libre, qui écrivent `user_verdict = down` au format historique de `user_verdict_reason` et archivent l'offre. « Lien mort » n'écrit que `closed_at` : ce n'est pas un avis, il n'entre pas dans l'apprentissage. Chaque geste s'annule pendant 5 secondes, et s'annule tout seul si l'écriture échoue — les events ne partent qu'après confirmation.

**Décision — trois zones.** « À décider » ne montre que les hot leads non triés entrés depuis moins de 7 jours : une offre non décidée en sort d'elle-même, il n'y a pas de file qui grossit. « Tes candidatures » porte le suivi et les issues (`interview`, `rejected`, `ghosted`, statuts ouverts par `sql/030` et jamais écrits jusqu'ici) ; les 30 candidatures sans date, antérieures au 2026-08-17, y sont repliées et se corrigent à la main. Le reste du scan garde la liste dense.

**Décision — les issues survivent aux republications (`sql/035`).** `jobs_inherit_user_status` traite `interview`, `rejected` et `ghosted` comme `applied` : hérités sans péremption, jamais forcés en `archived` par une clôture. Vérifié par un bloc `DO` qui lève son verdict en exception, donc sans rien persister.

**Ce qui est assumé.** La routine n'est pas modifiée : ses entrées changent seulement de sens — `applied` devient fiable, chaque « Pas pour moi » compte pour le seuil de 3 votes du recalibrage. Les 52 `applied` historiques ne sont pas corrigés automatiquement : l'ÉTAPE 7 continuera de lire comme positives les candidatures non corrigées, dont trois offres 👎 et pourtant `applied`, au recalibrage du lundi 2026-09-28 (décision séparée). « Ouvert » ne vit que dans la télémétrie : pas de colonne `opened_at` tant qu'un lot « apprentissage » n'en démontre pas le besoin. **Sonde de valeur**, lue le 2026-10-22 : si la part des hot leads décidés avant de sortir de la fenêtre de 7 jours ne dépasse pas le tiers d'ouverture mesuré avant ce changement, le geste unique n'a pas suffi. Spec : `docs/superpowers/specs/2026-09-24-jobs-radar-triage-design.md`.
